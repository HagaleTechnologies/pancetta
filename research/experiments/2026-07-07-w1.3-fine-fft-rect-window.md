## What this is

Design spec §3: the fine-FFT fallback (`extract_symbols_complex` / `par_extract_symbols_complex`,
`pancetta-ft8/src/decoder.rs`, gated at `sync_score >= 3.5` — the rescue path for candidates the
coarse spectrogram path couldn't decode) applies a Hann window to each symbol-length (1920-sample)
FFT. A Hann window on a one-symbol-period FFT destroys FT8's 8-FSK tone orthogonality: a tone at
exact bin center leaks ~-6 dB into its immediate neighbor bins under Hann, vs. an exact null under
a rectangular (i.e. no) window — precisely on the path meant to rescue the weakest candidates.

New `Ft8Config::fine_fft_rect_window: bool` (default `false`). When `true`, both fine-FFT
extraction twins use a rectangular window instead of Hann.

## Implementation

`self.symbol_window` (`Ft8Decoder`) is used **exclusively** by the fine-FFT fallback (confirmed by
grep before touching anything — no other caller reads it, serial or parallel). It's built once at
`Ft8Decoder::new()` and never mutated afterward (config is not hot-reloaded for this decoder), so
the flag is resolved once at construction rather than branched per-sample in the hot loop:

```rust
let symbol_window: Vec<f64> = if config.fine_fft_rect_window {
    vec![1.0; sps]
} else {
    (0..sps)
        .map(|i| 0.5 * (1.0 - (pi2 * i as f64 / (sps - 1) as f64).cos()))
        .collect()
};
```

Both `extract_symbols_complex` (serial) and `par_extract_symbols_complex` (parallel, via
`DecodeContext::symbol_window`) read this same field, so one construction-time branch covers both
twins with zero added runtime cost when the flag is off (byte-identical to the pre-existing Hann
path) and zero added branching when it's on.

Research-harness plumbing added (mirrors the existing `--pade-atanh`/`--escalation-enabled`
pattern): `DecoderUnderTest::with_fine_fft_rect_window` (`pancetta-research/src/decoder.rs`),
`--fine-fft-rect-window` CLI flag (`pancetta-research/src/bin/eval.rs`).

`test_complex_dft_tone_detection`), and calls the REAL `extract_symbols_complex` (not a
reimplementation) with two full `Ft8Decoder` instances — one Hann (flag off), one rect (flag on).

(bin-centered tone orthogonality)

The -6.01 dB figure lines up almost exactly with the spec's predicted "~-6 dB leakage into
adjacent tones" — independent confirmation the test is measuring the real effect, not an
artifact.

**GREEN** (real implementation restored): both assertions pass —
Hann-neighbor leakage >= -8 dB (documents the leakage being removed) and
rect-neighbor leakage <= -40 dB (bin-centered orthogonality), for both neighbor tones (2 and 4),
across every symbol in the synthetic signal.

Companion regression tests in `pancetta-ft8/tests/decoder_refinement_tests.rs`:

## Gate verdict

The plan's standing `[A/B]` gate requires ALL of:
1. Bootstrap-CI recall delta on hard-200 **excludes zero in favor** — **NOT MET**: CI is
   [-2, +11], includes zero, `compare` reports "NOT significant".
2. FP-on-noise tier = 0 new decodes — **MET** (3 -> 1, a decrease).
3. Unverified-novel increase <= 2xdelta-TP-increase — **MET** (+5 <= +8).
4. Speed plan's elapsed hard gate (no meaningful regression) — **MET** (51.2s -> 52.2s, +2%,
   noise-level for a hard-200 run; this task is not primarily a speed change).

Criterion 1 is not met, so the overall gate **does not pass**, despite every other signal —
hard-200 decode_rate WIN, hard-200 recall trending +4, hard-200 verified-novels down, synth-clean
SNR@50% WIN, FP-on-noise improving — pointing the same favorable direction. The honest read is
"probably real, not yet statistically distinguishable from noise on a 48/200-truth-coverage
sample" rather than "refuted." Forcing a flip on a trend that hasn't cleared the CI bar would
violate the plan's explicit discipline (`docs/superpowers/plans/2026-07-06-decoder-tp-sensitivity.md`
line 19: "flip only after the standing TP gate ... excludes zero in favor").

## Follow-ups (not part of this task, flagged for whoever picks this up next)

- **Widen truth coverage.** Only 48/200 hard-200 WAVs have a cached jt9 baseline in either
  worktree observed in this session. A fuller baseline cache (or a hard-1000 re-run, which the
  plan explicitly names as the recourse "for flips claiming <1% effects") would tighten the CI and
  might well cross the zero-exclusion bar given the consistent positive trend across three
  independent tiers.
- **The fine-FFT fallback's frequency search is still coarse** (0/±3.125 Hz, no sub-bin step) even
  with a rectangular window — design spec §3/D3 calls for a proper fine dt/df grid search (the
  bigger Workstream-3 lever) before a rect window's total lack of spectral tapering is fully safe
  against real-signal timing/frequency mismatch. That D3 work is out of scope for this narrow
  task but is the natural next step if this flag is revisited.
- Two new baseline cache files were copied into this worktree's gitignored
  `research/baselines/ft8/` (48 files, from the primary checkout) — not committed (matches the
  existing `.gitignore` convention), but worth knowing this worktree's cache coverage changed
  mid-session in case a later task in this worktree re-measures hard-200 and sees different
  absolute numbers than an earlier session did.
