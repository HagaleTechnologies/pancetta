# AP4 i3-bit injection fix (Workstream 1, Task W1.1)

**Date**: 2026-07-07
**Branch**: `worktree-decoder-tp-sensitivity`
**Status**: Bug fix (not an A/B-gated flag flip) + hard-200 measurement, logged per the plan's
own requirement that every task get an honest measurement entry regardless of outcome.

## What this is

Spec: `docs/superpowers/specs/2026-07-06-decoder-tp-sensitivity-design.md` §4. `ApLevel::Ap4`
(a-priori decoding level 4 — used when we're mid-QSO expecting the partner's RR73/RRR/73
confirmation) injected payload bits 74-76 (the `i3` message-type field) as `(0, 0, 0)`. RR73/RRR/73
are **i3=1** ("standard message" family); `i3=0` selects the FreeText/Telemetry/contest family,
which `Ft8Message::is_plausible()` unconditionally rejects. So AP4's own injected prior
contradicted the very message class it exists to help decode.

## Fix

`pancetta-ft8/src/ap.rs`, `inject_ap_llrs`'s `ApLevel::Ap4` arm: bits 74/75/76 now inject
`(false, false, true)` instead of `(false, false, false)`.

**Bit order verified empirically from this project's own encoder**, not by assumption
(`pancetta-ft8/tests/ap_i3_tests.rs::encoder_rr73_message_uses_i3_one`): encoded `"W1ABC K1DEF
RR73"`/`"RRR"`/`"73"`, extracted the real 77-bit payload via Gray-decode of the transmitted
symbols, and confirmed bits 74..77 = `(0, 0, 1)` in every case — i3 is packed MSB-first (matches
both `message.rs::parse_payload`'s `bits_to_u32(&payload[74..77])` and the encoder's
`for i in (0..3).rev() { payload.push((i3 >> i) & 1 != 0) }`).

TDD: `ap4_injected_i3_bits_match_encoder_rr73_ground_truth` failed RED before the fix
(`left: [false, false, false], right: [false, false, true]`) and passes GREEN after.

## A separate, more serious bug this surfaced (OUT OF SCOPE for W1.1, flagged for follow-up)

Attempting the brief's Step 3 (a full audio-domain "AP0 fails, AP4 rescues" end-to-end test)
surfaced a **pre-existing, independent bug** that means AP3 — and therefore AP4, which is gated
behind AP3's own callsign injection succeeding first — can **never survive
`ap_injection_survived`** in production, regardless of the i3 fix:

- `inject_ap_llrs`'s AP3/AP4 arms inject `qso.their_bits` (the DX's callsign) at payload offset 0
  and `my_call.bits` (our own callsign) at offset 28.
- Payload offset 0..28 is the `to_callsign` field (`n28a`, i.e. the *addressee*); offset ~29..57 is
  `from_callsign` (`n28b`, the *sender*) — confirmed against a real ft8_lib reference payload byte
  for byte (`K1DEF W1ABC -12`'s reference bytes decode `n28a = 10217236 = pack28("K1DEF")`, the
  `to_callsign`).
- For a real incoming message directed at us (the only kind we ever decode — we never decode our
  own TX), **we** are always `to_callsign` (offset 0) and **the DX** is always `from_callsign`
  (offset ~29). The current injection has this backwards.
- `decoder.rs::ap_injection_survived`'s AP3/AP4 arm (independently, correctly) requires
  `to_callsign == my_call.callsign` and `from_callsign == qso.their_call`. Since the injection
  forces the *opposite* assignment, the decoded `to_callsign` will (if BP honors the injected
  prior) equal the DX's call, not ours — so `to_base != my.callsign` and the check
  unconditionally returns `false`.
- There is **also** a separate 1-bit misalignment in the offset-28 injection (`inject_28_bits(...,
  28, ...)` vs. the true `from_callsign` field position 29..57), confirmed empirically:
  constructing a payload with `their_bits`/`my_bits` placed exactly where the injection targets
  them and parsing it directly produced `from_callsign = "100 JD"` instead of a real callsign — the
  shift corrupts the field regardless of which station's bits are placed there.

Net effect: **AP3 and AP4 are both structurally dead code in production today**, not just AP4 as
the brief's narrower framing assumed. This is a real, higher-impact finding, but it's a
change to a widely-shared function (`inject_ap_llrs`'s AP1/AP2 arms have the same offset
convention and are used on *every* decode candidate when `my_call` is set, not just QSO-state
AP3/AP4), several existing tests hard-code the current (backwards) offsets as "expected", and
`enumerate_a8_expected_texts`'s `dx`/`my` template ordering looks like it has the same swap. Fixing
it properly needs its own dedicated task with a full regression pass across AP1/AP2/AP3/AP4 and
the a8 templates — flagged to the plan as a new, higher-priority follow-up rather than folded into
this narrowly-scoped task.

Consequence for this task's Step 3: a full audio-domain end-to-end rescue demonstration is not
achievable honestly today (it would require either faking the callsign roles into a
degenerate/self-consistent-but-unreal configuration, or fixing the deeper bug above, which is out
of scope). `pancetta-ft8/tests/ap_i3_tests.rs` instead verifies the fix at the LLR-injection level
(`ap4_injected_i3_bits_match_encoder_rr73_ground_truth`, `ap4_only_changes_i3_bits_relative_to_ap3`)
plus the encoder ground-truth test — a genuine, mechanically-verified fix of the stated bug,
without a misleading "rescue" demo built on a scenario that can't occur in production.

## Hard-200 A/B result: exactly neutral (by construction), logged honestly

Ran `cargo run --release -p pancetta-research --bin eval -- --tier curated-hard-200 --mode ft8`
both before and after the fix (`git stash` / `git stash pop` around the two runs, same corpus,
same jt9-baseline cache, same machine).

**Result: byte-for-byte identical scorecards.** `wavs_processed`, `novel_decodes`,
`novels_verified`, `novels_unverified`, and every one of the 200 `per_wav_records` entries were
exactly equal between the before/after runs.

This is not a coincidence — it is the expected, structural result: `pancetta-research`'s
`ApContext` construction (`pancetta-research/src/decoder.rs`, all 3 call sites: chrono-replay,
rolling `recent_calls`, and the plain `with_ap_context` passthrough) **never sets `active_qso`** —
every site builds `ApContext { my_call: None, active_qso: None, .. }` or a `recent_calls`-only
context (`hb-043`'s my_call-less AP1/AP2 path). Grepped the entire `pancetta-research` crate
(including `examples/ap_recovery_ceiling.rs` and `examples/hb087_session2_ap_decode_microtest.rs`)
for `active_qso: Some` — zero matches. Since AP3/AP4 both gate on
`ap_context.active_qso.is_some() && ap_context.my_call.is_some()`
(`pancetta-ft8/src/decoder.rs` ~line 5000), **AP3 and AP4 cannot fire in any current hard-200
replay path, at all** — not "rare", structurally impossible with the harness as it exists today.
The brief's own prediction ("small positive or neutral... AP4 currently fires only in
WaitingForConfirmation QSO state, rare in corpus replay") undersold this: it's not rare, it's zero
opportunities.

(Aside, unrelated to this task: the `curated-hard-200` tier's `truth_decodes_total` /
`wsjtx_decoded` fields both came back `0` in this run, vs. `main.json`'s cached `8853`/`8853` —
looks like a stale jt9-baseline-cache/corpus-hash mismatch in this checkout, not something this
change could cause (confirmed identical before/after). Not investigated further; flagged here in
case it affects a future task's hard-200 run and needs `--bin baseline --tier curated-hard-200`
re-cached.)

## Bottom line

The i3 fix itself is correct, encoder-verified, and strictly beneficial (AP4's prior no longer
contradicts its own target message class) — but it cannot currently manifest as a measurable
hard-200 delta because of two independent facts: (1) the research harness never populates
`active_qso`, and (2) even where `active_qso` IS populated in production (the live coordinator),
the separate AP3-callsign-injection bug documented above means AP4 still can't survive
`ap_injection_survived`. Both are honestly logged rather than papered over. This task fixes the
one bug in its stated scope (i3 bits) and surfaces — without fixing — the other.
