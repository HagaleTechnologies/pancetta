# AP1-AP4 callsign-field injection ordering + offset fix (Workstream 1, Task W1.7)

**Date**: 2026-07-07
**Branch**: `worktree-decoder-tp-sensitivity`
**Status**: Bug fix + tests, controller-inserted (not in the original plan document). Extends the
finding from `2026-07-07-w1.1-ap4-i3-fix.md` (Task W1.1), independently re-verified here by
tracing the live source directly.

## What this is

`pancetta-ft8/src/ap.rs`'s `inject_ap_llrs` (the `ApLevel::Ap1`/`Ap3`/`Ap4` arms), plus its
companion helpers `inject_ap2_caller` / `inject_recent_call_at_called`, injected the 77-bit FT8
payload's two 28-bit callsign fields at the wrong offset AND with the wrong semantic role assigned
to each field.

## Ground truth (verified against `message.rs::parse_type1_standard`)

```
n29a = bits[0..29]   (29 bits: 28-bit callsign + 1 suffix-flag bit)
n29b = bits[29..58]  (29 bits: 28-bit callsign + 1 suffix-flag bit)
n28a = n29a >> 1  ->  message.to_callsign    (bits 0-27)
n28b = n29b >> 1  ->  message.from_callsign  (bits 29-56)
```

We are always the addressee (`to_callsign`) for any message we decode — we never decode our own
transmissions — so **our callsign always belongs at bits 0-27 (offset 0)** and **the other
station's callsign always belongs at bits 29-56 (offset 29)**. The two 28-bit fields are NOT
evenly spaced at offsets 0 and 28 — there's a 1-bit gap at bit 28 (the `to_callsign` suffix flag)
between them.

## The bug (confirmed before touching code)

| Function | Injected | Should be |
|---|---|---|
| `Ap1` (own call) | offset 28 | offset 0 |
| `Ap3`/`Ap4` own call | offset 28 | offset 0 |
| `Ap3`/`Ap4` QSO partner | offset 0 | offset 29 |
| `inject_ap2_caller` (candidate caller / `from_callsign`) | offset 0 | offset 29 |
| `inject_recent_call_at_called` (candidate called / `to_callsign`) | offset 28 | offset 0 |

`decoder.rs::ap_injection_survived` — written independently, in a different file — already
required the CORRECT assignment (`to_callsign == my_call` for Ap1/Ap2/Ap3/Ap4; additionally
`from_callsign == qso.their_call` for Ap3/Ap4). The hb-043 my_call-less recent-only path
(`RecentInjectPos`/`par_try_ldpc_with_recent_only`) also already verified correctly
(`RecentInjectPos::Caller -> from_callsign`, `RecentInjectPos::Called -> to_callsign`) — only the
underlying `ap.rs` injection offsets were wrong, confirming the verification side of the codebase
was right all along and only the injection side had the bug.

## Step 1: does AP1/AP2 share the bug, or did AP3/AP4 diverge from an already-correct pattern?

Verified directly from the code (not assumed): **AP1/AP2 share the identical bug.** `ApLevel::Ap1`
injected `my_call.bits` at offset 28 unconditionally, and `inject_ap2_caller`/
`inject_recent_call_at_called` used the same backwards offsets 0/28 that AP3/AP4 used. There was
no divergence — AP1-AP4 all shared one confused mental model, stated explicitly (and wrongly) in
`ap.rs`'s own module doc comment ("Bits 0-27: calling station callsign... Bits 28-55: called
station callsign") and in `RecentInjectPos`'s doc comments ("Inject at bits 0-27 (caller /
from-callsign position)" / "bits 28-55 (called / to-callsign position)").

## The fix

- `ApLevel::Ap1`: inject own callsign at offset 0 (was 28).
- `ApLevel::Ap3`/`Ap4`: inject own callsign at offset 0 (was 28), QSO partner at offset 29 (was 0).
- `inject_ap2_caller`: offset 29 (was 0) — a candidate caller is always `from_callsign`.
- `inject_recent_call_at_called`: offset 0 (was 28) — a candidate "called" station is always
  `to_callsign`.
- `enumerate_a8_expected_texts` (a8 sequenced-QSO-state AP template enumeration, Step 4 of the
  brief): swapped `"{dx} {my} ..."` to `"{my} {dx} ..."`. `Ft8Message::Display` renders
  `to_callsign` first (`"K1ABC W1AW RR73"` means to=K1ABC, from=W1AW), and we are always
  `to_callsign` in any message directed at us — confirmed the same swap the brief flagged as
  "looking similarly affected."
- `ap.rs`'s module doc header, `ApLevel`'s per-variant doc comments, `RecentInjectPos`'s doc
  comments, and the `ap_injection_survived`/call-site comments in `decoder.rs` were all corrected
  for accuracy (comment-only, no behavior change beyond what's listed above).
- `ap_injection_survived` itself was NOT changed — it was already correct, confirmed by tracing it
  against `message.rs` directly before touching anything (per the task's escalation criterion:
  "if that function ALSO has a bug you didn't expect" — it didn't).

**Out of scope, flagged but not touched**: `pancetta-ft8/src/a7.rs`'s `build_standard_pinned_mask`
labels a boolean PIN mask "callsign-A at bits 0-27, callsign-B at bits 28-55" — the same
off-by-one boundary confusion (real callsign-B/`from_callsign` starts at bit 29, not 28), but a7 is
a different mechanism (template cross-correlation against a full codeword produced by the real
encoder, not a manual value injection) and wasn't named in this task's brief. The mask only flags
*which* bits are structurally pinned for correlation purposes, not their values, so the impact (if
any) is a narrow, low-severity mis-boundary in the correlation window, not an inverted/backwards
injection. Left alone per the brief's "keep the fix surgical" instruction.

## The end-to-end rescue test (`pancetta-ft8/tests/ap_injection_ordering_tests.rs`)

Building a genuine "AP0 fails, AP3 rescues" test took real iteration — a naive design does NOT
discriminate between the buggy and fixed injection at every severity, which is worth recording
since it's a real (if narrow) empirical nuance in the original bug write-up's own reasoning.

**What didn't work and why**: corrupting/erasing the callsign-field audio (localized noise burst
over just the data tones carrying payload bits 0-56, tones 7-25) while leaving the rest of the
codeword pristine produces an "AP0 fails, AP-context succeeds" pattern — but the SAME pattern
appears with the pre-fix (backwards) injection too, at every severity tested (local SNR from -30
to -100 dB). Root cause: `inject_bit` fully OVERWRITES the channel LLR (doesn't blend with it), so
at total local erasure any sufficiently confident prior — right or wrong — breaks LDPC belief
propagation out of a degenerate near-zero-LLR deadlock; with ~118 of 174 codeword bits left
completely clean (83 parity checks + 20 clean payload bits), that's enough redundancy for BP to
reconverge on the one globally-consistent codeword regardless of what was fed in at the "erased"
56 positions. This means the earlier brief's confident claim that AP3/AP4 "have likely never
produced a single additional real decode" is not fully supported empirically at extreme local
corruption — under that specific regime, the bug's wrong values still happened to unstick BP the
same as correct values would, because the redundant remainder alone determined the answer. This
is a real, if narrow, empirical caveat worth recording rather than glossing over.

**What discriminates**: thinning the redundant remainder too — global (whole-window) noise at a
level where AP0 alone starts to struggle, PLUS the same targeted callsign-field noise burst, so the
"other" 118 bits are no longer clean enough to out-vote a wrong 56-bit bias within available LDPC
iterations. At the crate's **default** `Ft8Config` (`ldpc_iterations = 100`, all other defaults),
global SNR = -28 dB (whole 12.64s window) + an extra -20 dB burst localized to data tones 7-25
(payload bits 0-56) is a clean discriminator:

- Message: `"K1ABC W1AW RR73"` (K1ABC mid-QSO with W1AW, awaiting RR73 — `QsoApProgress::
  WaitingForConfirmation`, the state that gates AP4 in production).
- **AP0** (no context): fails to decode, both before and after the fix (confirms the test scenario
  is genuinely hard, not gamed).
- **Fixed injection**: `decode_window_with_ap` with `my_call=K1ABC`, `active_qso=W1AW` rescues it,
  reported as `ap_level = 3` (AP3, not AP1/2 — confirms the rescue used both callsigns' priors, not
  a coincidental AP0-equivalent hit).
- **Pre-fix (buggy) injection**: verified manually — `git stash push -- pancetta-ft8/src/ap.rs` to
  revert only the injection code (config, audio bytes, everything else held byte-identical via the
  deterministic fixed-seed noise generator — checksum matched exactly, `-1070.0650230356841`, both
  runs) — the SAME scenario does NOT rescue: `AP decodes: []`. Restored the fix afterward
  (`git stash pop`) before writing the permanent test.

This is exactly the differential proof the task's self-review checklist asks for: same audio, same
config, only the injection code differs, and the fix is what flips the outcome from "buggy code:
no rescue" to "fixed code: rescue". The permanent test in `ap_injection_ordering_tests.rs` asserts
the "fixed code rescues" half of this (the only half that can live in the repo without literally
un-fixing the bug); the buggy-code-fails half is recorded here as the differential verification
performed during development.

## Test results

- `cargo test --features transmit -p pancetta-ft8`: all 15 test binaries green (including the new
  `ap_injection_ordering_tests.rs` and the updated `ap.rs`/`decoder.rs` unit tests).
- `cargo test --workspace --features transmit`: full workspace green, 91 `test result: ok` blocks,
  zero failures, zero panics.
- **No existing WAV-fixture decode counts changed** (`wav_decode_tests.rs`,
  `ft8lib_crossval_tests.rs`, `round_trip_tests.rs`, etc. — zero diff, byte-identical to before this
  change): none of the existing fixture-based tests exercise QSO-state AP (`my_call` +
  `active_qso` together); they either call `decode_window` (AP0) or use a default/empty
  `ApContext`. This is NOT a bit-exact task by design (AP3/AP4 can now genuinely rescue decodes
  they never could before), but there happened to be no fixture in this corpus that exercises the
  changed path, so the observed decode-count-unchanged result is expected, not a sign the fix is
  inert — the new synthetic rescue test proves the path is now live.
