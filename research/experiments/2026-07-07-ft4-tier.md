# FT4 evaluation tier — first-ever FT4 decode sensitivity baseline (Workstream 0, Task W0.4)

**Date**: 2026-07-07
**Branch**: `worktree-decoder-tp-sensitivity`
**Status**: HARNESS — new evaluation tier + first-ever measurement. No decoder code changed in
this task (pure harness/corpus/plumbing addition, per the task's [HARNESS] gate).

## What this is

FT4 (the faster, 7.5s-slot, 4-GFSK sibling of FT8) shipped in production (`pancetta-ft8`'s
`ProtocolParams::ft4()`, wired end-to-end into the coordinator per CLAUDE.md's "FT4 mode"
bullet), but its decode *sensitivity* had never been measured — only encode/modulate round-trips
existed (`pancetta-ft8/tests/round_trip_tests.rs`). The design spec (§2) flagged this as an open
gap: "the decoder ships FT4 paths whose recall could be anything." This task builds the
measurement (an FT4 evaluation tier, mirroring the FT8 `synth-clean` tier W0.2 just calibrated)
and reports the first real number.

jt9's FT4 CLI flag (`-5`/`--ft4`) was pre-confirmed by the task brief before this task started
(via `jt9 --help` on the installed WSJT-X binary) — no re-investigation needed here.

## What was built

1. **`Mode::Ft4`** (`pancetta-research/src/mode.rs`) — added alongside `Mode::Ft8`, with a
   `Default` impl (`Mode::Ft8`) so `SynthConfig`'s new `mode` field back-compat-deserializes
   every pre-existing committed synth config with no `mode` key at all.
2. **Protocol-generic synth generation** (`pancetta-research/src/synth.rs`) —
   `modulate_message_at_protocol(text, base_freq_hz, &ProtocolParams)` encodes + modulates via
   `pancetta_ft8::Ft8Encoder::with_protocol` / `encode_message_protocol` /
   `Ft8Modulator::modulate_symbols_protocol` (the same protocol-aware API
   `pancetta-ft8/tests/round_trip_tests.rs`'s FT4 round-trip tests already exercise).
   `modulate_message_at` (the FT8 path used by every existing synth tier) is now a thin wrapper:
   `modulate_message_at_protocol(text, freq, &ProtocolParams::ft8())`. **Reuses
   `add_awgn_2500hz_ref` (Task W0.2's calibrated noise-scaling formula) completely unchanged** —
   that function is protocol-agnostic (a function of sample rate and signal RMS only), so no
   FT4-specific noise-scaling code was written at all. Guarded by a byte-identical-output
   regression test (`modulate_message_at_matches_protocol_path_for_ft8`) so the refactor can't
   silently change FT8's existing synth corpora.
3. **FT4 corpus generation** (`pancetta-research/src/bin/gen_synth.rs`) — `SynthConfig.mode`
   selects `ProtocolParams::ft4()` + FT4-scaled slot geometry: 7.5 s slot (90,000 samples @ 12
   kHz, vs FT8's 15 s / 180,000), 0.5 s lead-in (vs FT8's 1.0 s), ±0.15 s dt range (vs FT8's
   ±0.3 s) — all halved from FT8's to match FT4's halved slot, preserving the same proportional
   margin (FT4 active message 5.04s / 7.5s slot ≈ FT8's 12.64s / 15s slot). Base-frequency range
   (400-2600 Hz) reused unscaled — FT4's 4 tones span only ~62.5 Hz, comfortably inside it
   regardless of mode.
4. **FT4 corpus config**: `research/corpus/synth/manifests/ft4_clean.config.json` — same shape as
   W0.2's `clean.config.json`: 50 messages x 11 SNR steps (−24 to −14 dB, 1 dB steps) = 550 WAVs,
   `"mode": "ft4"`.
5. **jt9 oracle, mode-aware** (`pancetta-research/src/bin/baseline.rs`) — `run_jt9` now takes
   `mode: Mode` and selects `-8` (FT8) vs `-5` (FT4) accordingly. **Found and fixed a real
   harness bug while wiring this**: jt9's decode-line submode marker (5th field) differs by
   mode — `~` for FT8, **`+` for FT4** (confirmed empirically: `000000 -14 -0.1 1552 +  CQ K1AAA
   FN42` from a real generated FT4 WAV; not documented in `jt9 --help`). The pre-existing
   `parse_jt9_line` hardcoded `~`, which would have silently discarded every FT4 decode line
   (zero recall reported, looking exactly like a broken decoder rather than a broken parser).
   Fixed via `jt9_submode_marker(mode)`; verified against real jt9 output for both modes before
   committing.
6. **`synth-ft4` eval tier** (`pancetta-research/src/bin/eval.rs`) — dispatches
   `run_synth_tier` (now `mode`-parameterized, so the jt9-baseline-cache lookup reads
   `research/baselines/ft4/` instead of hardcoded `research/baselines/ft8/`) against the new
   corpus. Refuses to run unless invoked with `--mode ft4` (the decoder must be constructed with
   `Protocol::Ft4`, or it would demodulate FT4 audio as FT8 — wrong symbol/tone geometry, not a
   graceful degradation). Also added `--synth-ft4-manifest` (mirrors `--noise-manifest`) so tests
   can point the tier at a small generated manifest instead of the full 550-file corpus.
7. **Decoder-construction refactor** (`pancetta-research/src/bin/eval.rs`,
   `pancetta-research/src/decoder.rs`) — the ~190-line CLI-knob-to-`Ft8Config` wiring chain in
   `main()`'s old `match args.mode { Mode::Ft8 => { .. } }` arm is entirely generic
   `Ft8Config` fields, not FT8-specific, so it was factored into `build_decoder_from_args(args,
   protocol)` and shared verbatim between FT8 and FT4 rather than duplicated. `Ft8Decoder::
   with_protocol` (new builder) sets `Ft8Config::protocol`; `DecoderUnderTest::mode()` now
   derives its reported `Mode` from `self.config.protocol` instead of hardcoding `Mode::Ft8`.
   Regression-verified: `eval_fixtures.rs` (FT8 fixtures tier, exercises this exact refactored
   path) and `synth_roundtrip.rs` (FT8 synth-clean sanity) both still pass unchanged.
8. **Tests**: `pancetta-research/tests/ft4_tier_tests.rs` — generates a tiny 4-WAV FT4 corpus
   directly via the library functions (not the CLI), runs the real `eval` binary's `synth-ft4`
   tier over it via `--synth-ft4-manifest`, and asserts (a) the tier processes all 4 WAVs and
   populates `by_snr_db`, (b) a clean −5 dB FT4 WAV is actually decoded (sanity that FT4 decoding
   isn't fundamentally broken — not a production SNR-threshold claim), (c) the tier refuses to
   run under `--mode ft8`. Plus 3 new unit tests in `synth.rs`/`mode.rs` (FT4 round-trip JSON,
   FT4-vs-FT8 protocol-generic modulation, byte-identical-refactor guard).

   **Harness bug caught by this test while writing it**: the test's `SynthEntry.wav_path` was
   initially set to a workspace-relative path (`"wavs/<file>.wav"`), but the test's WAVs live in
   a tempdir *outside* the real workspace root — `load_synth_corpus` resolves every entry via
   `workspace_root.join(&e.wav_path)`, so the tier was silently trying to open nonexistent files
   under the real repo root and reporting 0 decodes everywhere (a decode error is counted as a
   failed attempt, not surfaced as an error — this is itself a minor harness sharp edge, noted
   below). Root-caused via a standalone debug script that proved the same generation+decode
   logic worked correctly in isolation; fixed by storing the tempdir's *absolute* WAV path in the
   entry (`Path::join` on an absolute path discards the base and returns it as-is, which is
   exactly what's needed here).

## The measurement

### jt9 FT4 oracle run

```
cargo run --release -p pancetta-research --bin baseline -- \
  --tier synth --mode ft4 \
  --synth-manifest research/corpus/synth/manifests/ft4_clean.manifest.json
```

- 550 WAVs, jt9 invoked as `jt9 -5 -d 3` per WAV.
- jt9 binary: `/Applications/wsjtx.app/Contents/MacOS/jt9`.
- Elapsed: ~27 seconds total (much faster than FT8's ~2.7-3.2 s/WAV — FT4's audio is half the
  duration and jt9's own FT4 decode path is evidently fast).
- Cached to `research/baselines/ft4/<wav_sha256>.json` (550 new cache files).

### pancetta eval run

```
cargo run --release -p pancetta-research --bin eval -- \
  --tier synth-ft4 --mode ft4 \
  --output research/scorecards/w04_ft4_scorecard.json
```

No CLI overrides — `Ft8Config::default()` with `protocol = Protocol::Ft4`, the exact production
config FT4 QSOs actually run under today. Elapsed: 267.1 s for 550 WAVs (~0.49 s/WAV) — the
harness's default `decode_window` native-Rust path, not the ~25x-faster protocol-aware C
`ft8_lib` FFI path mentioned in prior FT4 timing-margin work (that path is a separate opt-in
performance lever, not what determines production recall by default).

## Result — first-ever FT4 sensitivity curve

| SNR (dB) | pancetta decoded/50 | jt9 decoded/50 |
|---:|---:|---:|
| −24 | 0 | 0 |
| −23 | 0 | 0 |
| −22 | 0 | 0 |
| −21 | 0 | 0 |
| −20 | 0 | 1 |
| −19 | 0 | 9 |
| −18 | 0 | 40 |
| −17 | 0 | 48 |
| −16 | 3 | 50 |
| −15 | 13 | 50 |
| −14 | 39 | 50 |

- **jt9 `snr_at_50pct_recovery_db` = −18.484 dB** (interpolated between −19 dB [9/50=0.18] and
  −18 dB [40/50=0.80]). Sanity check: this lands close to WSJT-X's commonly cited "FT4 is a few
  dB less sensitive than FT8" characterization (this corpus's FT8 jt9 curve, from W0.2, hit 50%
  at −21.3 dB — so jt9's own FT4 curve sits ~2.8 dB worse than its FT8 curve here, consistent
  with FT4's shorter 7.5s transmission carrying less total signal energy per symbol count).
- **pancetta `snr_at_50pct_recovery_db` = −14.538 dB** (interpolated between −15 dB [13/50=0.26]
  and −14 dB [39/50=0.78]).
- **pancetta `snr_at_90pct_recovery_db` = None** — pancetta never reaches 90% recall anywhere in
  this corpus's tested range (its best bin, −14 dB, is only 78%).

### Headline number

**pancetta SNR@50% − jt9 SNR@50% = −14.538 − (−18.484) = +3.95 dB.**

This is a **substantially larger gap than FT8's** (W0.2 measured pancetta needing +2.10 dB more
SNR than jt9 for 50% recall on FT8). FT4 recall is genuinely, surprisingly worse relative to jt9
than FT8's already-known gap — almost double the dB deficit. This is the honest finding, not
smoothed over: **pancetta's FT4 decode sensitivity has a real, previously-unmeasured
deficiency**, distinct from (and larger than) the general FT8 sensitivity gap the rest of this
plan targets.

Additionally: pancetta's own curve **never reaches 90% recovery** anywhere in the −24..−14 dB
range tested (jt9 reaches 100% by −16 dB), meaning even at this corpus's most favorable SNR step
pancetta misses roughly 1 in 5 clean FT4 signals — a hard ceiling within this SNR window, not
just a rightward-shifted threshold.

## Interpretation — plausible root cause (not fixed here, [HARNESS] scope)

Not investigated further per the task's [HARNESS] gate (no decoder behavior change permitted),
but flagged as a real, likely-productive lead for a future workstream: FT4's Costas sync
structure is meaningfully different from FT8's — 4 short (4-symbol) sync groups spread across
the transmission vs FT8's 3 long (7-symbol) groups — giving less total correlation gain per
candidate. Every sync-related `Ft8Config` default (`min_sync_score`, `max_sync_candidates`,
`nms_*` thresholds, the various `sync_time_interp_*` refinement knobs) was empirically tuned
against FT8 signals only; if those thresholds don't transfer to FT4's shorter/weaker Costas
correlation, real FT4 signals could be getting filtered out of the sync-candidate list before
LDPC ever sees them — independent of SNR, which would explain both the large 50%-threshold shift
*and* the sub-90% ceiling (a floor effect rather than a smooth SNR-only sensitivity curve).
**This is exactly the kind of "FT4-specific failure becomes a ticket" outcome the task brief
anticipated** — logged here as a candidate hypothesis for whichever future workstream tackles
FT4 sensitivity, not diagnosed further in this harness-only task.

## Harness sharp edge noted (not fixed, out of scope)

`run_synth_tier`'s `Err(_) => { /* Decode error — counts as failed attempt. */ }` branch
(`eval.rs`) silently swallows decode errors (e.g. a genuinely missing/misconfigured WAV file)
into the same "0 recall" bucket as a real sensitivity miss. This is pre-existing behavior
(unchanged by this task) that made the test-authoring bug described above harder to diagnose than
necessary — worth a future harness hardening pass (e.g. a distinct `errored` counter in
`TierResult`) but out of scope for this [HARNESS] task, which only adds the FT4 tier.
