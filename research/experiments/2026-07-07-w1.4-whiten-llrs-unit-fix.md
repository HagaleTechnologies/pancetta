# `whiten_llrs` dB/linear-magnitude unit-consistency fix + gain-invariance (Workstream 1, Task W1.4)

**Date**: 2026-07-07
**Branch**: `worktree-decoder-tp-sensitivity`
**Status**: Implemented + investigated + A/B'd on the Workstream-0 gates. **Gate PASSED in favor of
flipping `Ft8Config::llr_whitening_enabled` default from `true` to `false`** — turning whitening
OFF after the unit fix recovers +56 TPs on hard-200 (bootstrap CI excludes zero), with zero
regression on the FP-on-noise tier and a favorable unverified-novel delta. Default flipped.

## What this is

Design spec §7: `whiten_llrs` (`pancetta-ft8/src/decoder.rs`) divides each data symbol's LLRs by a
per-tone x per-symbol noise-magnitude estimate (median-based), floored at `NOISE_FLOOR = 1e-6`.
The floor and median logic are calibrated for LINEAR magnitude (`|y|`, the fine-FFT path's native
units) but several spectrogram-path callers hand it dB LOG-POWER values instead
(`10*log10(mag^2)`, commonly negative). A negative dB value fed into a floor calibrated for a
strictly-positive linear magnitude always clamps to the floor regardless of its actual value —
this is a real dimensional-consistency bug, independently confirmed both by code inspection and by
instrumented empirical measurement during this task (below).

## Investigation: does the gain-invariance bug actually manifest as predicted?

The task brief (citing spec §7) predicted: "with negative dB input values, the 1e-6 floor
degenerates it to a near-no-op, so its measured benefit is input-gain dependent." The literal
prediction is that decoding the SAME signal at two different absolute gains would decode a
DIFFERENT message set, because the floor would trigger differently at different gains.

**Empirical check (pre-fix code, real off-air fixture `wsjt/210703_133430.wav`, 9 messages at
gain 1.0):** temporarily instrumented `whiten_llrs` to log how often the per-tone median array
was fully floored (all 8 tones at `NOISE_FLOOR`) vs not floored at all, across every candidate
evaluated during decode. Result: **out of 3884 invocations, 715 (~18%) were fully floored** (a
degenerate, non-differentiating divisor) and 3169 were not floored at all. This confirms the
"near-no-op on a real fraction of calls" half of the prediction.

**However, decoding the same fixture at gain 1.0 vs gain 0.01 (the literal test the brief
prescribes) produced IDENTICAL decode sets** (all 9 messages, both gains) — and so did a much
wider sweep, **gain in {0.0001, 0.001, 0.01, 0.1, 1.0, 5.0, 20.0, 100.0}** (six orders of
magnitude, -80 dB to +40 dB relative to native level): every gain decoded the exact same 9-message
set. Re-running the floor-hit instrumentation at gain 1.0 vs gain 0.01 showed the **identical**
3169/715 split at both gains — i.e., on this real recording, whichever calls floor do so
regardless of gain (their raw dB values are apparently comfortably clear of the ~40 dB shift window
either direction), and whichever calls don't floor also don't at either gain (their values are the
fine-FFT `|y|` population, whose magnitudes stay comfortably above `1e-6` even after a 100x gain
cut).

**Honest finding**: the dimensional bug is real (confirmed both by code inspection and by the
floor-hit instrumentation), but on this real fixture it manifests as a **persistent partial
no-op** (~18% of dB-path calls degenerate to a constant divisor, independent of gain) rather than
as a **gain-dependent flip** in the decoded message set. The brief's literal prediction (decode set
changes between gain 1.0 and gain 0.01) does NOT hold on this fixture — this is reported honestly
per the task's own instruction to investigate rather than assume. The underlying bug is still a
genuine dimensional-consistency defect worth fixing regardless of whether THIS specific gain pair
happens to expose it as a flip.

## Implementation

`whiten_llrs` and `maybe_whiten_llrs` gained a `units: ToneUnits` parameter (the same enum already
used by the sibling `impulse_robust_weight_llrs`/`maybe_impulse_robust_llrs`, added by an earlier
task for exactly this dB-vs-linear-magnitude split). Before any median/floor math runs,
`ToneUnits::Db` input is converted to linear magnitude via a new `tone_magnitudes_linear_from_db`
helper (`10^(db/20) == sqrt(power)`); `ToneUnits::LinearMag` input passes through unchanged
(zero-alloc, byte-identical to pre-fix behavior on the fine-FFT callers, which were already
correct). All 10 call sites were updated with the correct unit tag, read directly off the
neighboring `maybe_impulse_robust_llrs` call at each site (which already carried the correct
`ToneUnits::{Db,LinearMag}` for that exact `tone_magnitudes` variable) — 8 call sites are
`ToneUnits::Db` (spectrogram path), 2 are `ToneUnits::LinearMag` (fine-FFT path,
`extract_symbols_complex`/`par_extract_symbols_complex`).

## Gate verdict

The plan's standing `[A/B]` gate requires ALL of:
1. Bootstrap-CI recall delta on hard-200 excludes zero in favor — **MET**: Δ=+56 TPs favoring
   OFF, 95% CI [+34, +80], entirely positive (`compare` reports "significant"). The effect size
   (+56 of 1195, ~4.7%) is well above the "<1% effect" threshold that would require escalating to
   hard-1000.
2. FP-on-noise tier = 0 new decodes — **MET**: FP count DECREASED (2 → 1) with whitening off; no
   increase.
3. Unverified-novel increase <= 2x delta-TP increase — **MET**: switching ON→OFF, unverified-novel
   count increases by 40 (1755→1795) alongside the +56 verified-TP increase; allowance =
   2×56 = 112, and 40 <= 112 comfortably. (Verified-novels also increase, +102 — i.e. most of
   OFF's extra decodes are independently truth-confirmed, not just unverified noise.)
4. Speed plan's elapsed hard gate (no meaningful regression) — **MET**: hard-200 ~51s both configs
   (unchanged), noise_1000 819s → 840s (+2.6%, within run-to-run noise for a tier this heavy, and
   this task is not a speed change), synth-clean ~470s → ~455s (no regression).

All four criteria are met, and uniquely for this task, **in favor of the OPPOSITE of the
production default** — i.e. the gate says to flip `llr_whitening_enabled` from `true` to `false`.
This is the mirror image of the more common "flip a default-off flag to on" pattern: here the
already-on default was accepted years earlier against buggy code, and the honest re-measurement
after fixing that bug says the technique should be OFF.

## Decision

**Flip `Ft8Config::llr_whitening_enabled` default from `true` to `false`.** Updated:
- The field doc comment and the `Ft8Config::default()` construction site
  (`pancetta-ft8/src/decoder.rs`), both now recording the Batch 53 → Task W1.4 history.
- The regression test pinning the default, renamed `default_config_keeps_whitening_on` →
  `default_config_keeps_whitening_off` (inverted assertion), same file.

This is NOT a revert of the W1.4 unit fix — the fix itself (dB/linear-magnitude consistency,
gain-invariance) is correct and stays in. What changes is the *setting* of the (now-correct)
`llr_whitening_enabled` flag, re-measured honestly per the task's explicit instruction to "keep
whichever of {fixed-whitening-on, off} wins under the standing gate" rather than defaulting to
"on" because that was the pre-existing production stance.

## Interpretation: why did fixing a "near-no-op" bug make things worse?

Before the fix, the dB-path whitening was internally inconsistent: ~18% of its invocations
(measured on a real fixture, see Investigation above) degenerated into a constant, non-
differentiating divisor because dB values are commonly negative and the `NOISE_FLOOR = 1e-6`
floor (calibrated for strictly-positive linear magnitude) clamped them. The ORIGINAL Batch 53
"+4 TP / -713 FP" graduation measurement was therefore made against a whitening implementation
that was only PARTIALLY and INCONSISTENTLY active — a weak, diluted version of the intended
effect. Once fixed to apply consistently and correctly on every call, the median-based divisive
normalization is a much stronger effect, and that stronger effect turns out to cost real recall
(-56 TPs) on hard-200: a plausible mechanism is that per-symbol noise medians computed from only
7 non-winner tone samples are noisy estimates, and now-consistent full-strength scaling can
over-amplify or over-suppress individual symbols' LLRs in a way that occasionally flips a
borderline LDPC decode from success to failure. This task does not further diagnose the exact
failure mode (out of scope) — the standing gate's job is exactly to catch this kind of "looks
plausible, doesn't survive contact with real measurement" case, and it did.
