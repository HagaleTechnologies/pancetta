## Ranked candidates

### Rank 1 — CE3TSK/jtdx_contest: Extended Same-Parity Hint Memory (1 → 4 periods) [hb-280 draft]

**Technique:** GitHub repository `ce3tsk/jtdx_contest` (Tihomir Sokcevic, CE3TSK).
GPL-3.0 fork of JTDX 2.2.159 with a rebuilt FT8/FT4 decoder. The fork extends the
within-session "hint" AP mechanism from the standard JTDX 1-period window to a 4-period
rolling window. After each decoded period, the fork accumulates decoded callsigns; when
decoding the next same-parity period, any callsign decoded within the last four
same-parity periods is treated as a known-call hint (injected as known bits in the AP
decode pool for the next slot). The ablation table in the companion paper reports
this extended window accounts for approximately +6% more FT8 messages on-air, at no
measurable wall-clock cost once the callsign list is maintained.

Companion paper: "Deterministic Ensemble Decoding for FT8 and FT4: Re-Reading the Same
Audio," CE3TSK. Available at ce3tsk.com (PDF).

**Measured evidence (from CE3TSK companion paper and README):**

| Metric | CE3TSK ensemble (full) | JTDX same recipe | Method |
|---|---|---|---|
| FT8 messages (240-period capture) | 6,208 | 5,249 | On-air, 1 hour recording |
| FT8 gain vs JTDX same recipe | +18.3% | — | Author-reported |
| FT8 gain vs JTDX as-shipped | +27.5% | — | Author-reported, lookup-off baseline |
| Ablation: hint memory 1→4 | **+6%** | — | Ablation table |
| Ablation: opposite recipe pass | +4.9% | — | Ablation table |
| Ablation: ensemble diversity | +15.3% | — | Ablation table |
| Ablation: pipeline total | +30.8% | — | Ablation table |

All figures are author-reported from one on-air recording. No independent replication
found.

**Primary source:**
- Repository: https://github.com/ce3tsk/jtdx_contest (last confirmed active; multiple forks)
- Paper: https://ce3tsk.com/download/JTDX_CONTEST_DECODER_PAPER.pdf
- Decoder explainer: https://ce3tsk.com/FT8_DECODER.pdf

**Applicability to pancetta:**
- The technique maps directly to pancetta's existing AP infrastructure
  (`pancetta-ft8/src/ap.rs`). The AP framework already supports injecting callsign bits as
  known; extending the hint pool from 1 period to 4 periods requires maintaining a
  `VecDeque<HashSet<Callsign>>` (or similar) in `Ft8Decoder`'s state, indexed by
  same-parity slot distance (0, 2, 4, 6 slots = same parity at 15s each), and feeding
  it into the AP hint pool at decode time.
- **Relationship to existing bank:** hb-173 (Within-QSO pair-conditional AP templates)
  uses decoded callsigns differently: it generates structured message templates from the
  current QSO partner (not an open pool). hb-175 (Cross-session ADIF-driven AP pool)
  draws from persisted ADIF, not from the live session. hb-048 (AP type 7) performs
  template cross-correlation (a richer, more expensive mechanism). hb-280 is simpler
  than any of these: live accumulation over 4 same-parity periods, no template
  generation, no ADIF dependency.
- **Incremental implementation cost:** low. The hint pool is a small data structure;
  integration with the AP inject point is a few lines. The main risk is FP inflation
  (injecting a wrong callsign from a stale hint). The ablation evidence suggests
  the net effect is positive, implying the FP rate from stale hints is dominated by the
  TP rate from fresh ones. A sweep over window length (1, 2, 3, 4 periods) on the
  eval harness will characterize this.
- **Relationship to pancetta's coordinatorstate:** `Ft8Decoder` already has a
  `recently_decoded_calls` structure (used by the callsign-continuity filter, hb-052).
  The 4-period hint pool is compatible with this, extending it to feed AP injection
  rather than just FP filtering.
- **License note:** GPL-3.0. The TECHNIQUE (rolling hint pool, 4-period window, AP
  injection from live decoded callsigns) is algorithmically obvious once described; no
  source copying required. Clean-room implementation works directly from the description
  in the companion paper without reading the fork's Fortran/C++ source.

### Rank 2 — CE3TSK/jtdx_contest: Orthogonal-Recipe Diversity Residual Pass [hb-281 draft]

**Technique:** Same fork as hb-280. After the primary decode pass (Recipe A), the fork
runs a second pass with an "opposite recipe" (Recipe B — orthogonal parameter set) over
the residual audio. The key distinction from pancetta's shelved hb-030/031 (multi-pass
with the same parameters) is that Recipe B is chosen specifically to explore the
error basins that Recipe A does NOT cover: if Recipe A uses aggressive OSD, Recipe B
uses aggressive BP; if A is high-sync-cap, B is low-cap-with-different-LLR. The fork
calls these "complementary" configurations, determined empirically to maximize the
fraction of messages Recipe B finds that Recipe A missed.

The ablation table attributes approximately +4.9% FT8 messages to the opposite-recipe
pass in isolation (after Recipe A, before ensemble diversity). This is distinct from
the ensemble contribution (+15.3%) and the hint memory contribution (+6%).

**Primary source:** Same as hb-280 (ce3tsk.com companion paper).

**Applicability to pancetta:**

- pancetta's current production decoder is single-pass (hb-031 graduated 2026-05-23),
  with multi-pass shelved because re-running the same parameters on the residual added
  overhead with minimal gain (hb-030/031 outcome). The CE3TSK ablation suggests the
  missing ingredient was **parameter diversity**: running different parameters covers
  different error basins, not just more computation.
- The architectural path: add a second `Ft8DecoderConfig` ("B recipe") that is
  parameter-orthogonal to the production config (e.g., Recipe A: high OSD, low
  sync_cap; Recipe B: low OSD, high sync_cap and more BP iterations). After Recipe A
  decodes and subtracts, Recipe B runs on the residual. Only messages not found by
  Recipe A are retained.
- **Why this is different from hb-030/031:** hb-031 shelved multi-pass because
  "multi-pass was overhead, not capability" — but that evaluation used IDENTICAL
  parameters on each pass. CE3TSK's result is that the ORTHOGONALITY of the second
  recipe is the source of the gain. The parameter space to search for a good Recipe B
  is the same space pancetta already sweeps for Recipe A; the orthogonal pair is a new
  optimization target.
- **Interaction with subtract quality:** the residual quality determines how well Recipe
  B can distinguish real signals from artifacts of imperfect subtraction. This was not
  a bottleneck in hb-030/031 (at single-pass subtraction quality); the same caveats
  apply here, but are relevant only if Recipe B is aggressive enough to pick up subtraction
  artifacts.
- **License:** same as hb-280 (GPL-3.0; concept is architecturally obvious once stated).

### WSJT-X 3.3.0-beta6 (Nov 11) and beta8 — two new betas

**Beta6** was released 2026-11-11 (source: GitHub WSJTX/wsjtx releases). **Beta8** is a
subsequent release (exact date not confirmed in search results). Beta8 changelog items
relevant to FT8:

1. **OSD pass on bit-packed vectors** (Roger Rehr, "ft8: run the OSD on bit-packed
   vectors"): performance optimization only. No sensitivity change. This is a bit-packing
   improvement to the OSD inner loop, reducing memory bandwidth per OSD step. Not
   bank-worthy for sensitivity, but confirms the upstream OSD implementation is being
   actively optimized — alignment with pancetta's OSD engine worthwhile to check.

2. **Subtraction filter: running sums instead of FFTs** (Roger Rehr, performance change):
   performance optimization only. No sensitivity change.

3. **a8 candidate list includes /R and /P DX calls**: correctness fix. WSJT-X's a8 AP
   pass (decode at HisCall nfqso frequency) now includes portable (/P) and rover (/R)
   call variants in the candidate list. This is a correctness item for pancetta's AP
   paths: confirm that pancetta's AP injection includes /R and /P call variants when
   HisCall ends with these suffixes (or that the AP template generator handles compound
   callsigns). Check `pancetta-ft8/src/ap.rs` AP type 8 path and compound-callsign
   handling in `pancetta-core/src/types/callsign.rs`.

**Still open from Nov 2 scan:** RR73 packing compatibility check — confirm
`pancetta-ft8/src/pack.rs` and AP RR73 path (`pancetta-ft8/src/ap.rs`) are bit-for-bit
compatible with WSJT-X 3.3.0-beta4+ "acknowledgment" packing change before GA. This

## Noted but not bank-worthy

### sdrtop v0.7.1 "almost a dB more sensitivity"

The sdrtop v0.7.1 release page claims "almost a dB more sensitivity" from a timing fix
(comparison against WSJT-X found a timing loss on weak signals, now fixed). The decode
count comparison (242 messages vs WSJT-X's 237 normal / 245 deep) does not support a
1 dB gain claim; this appears to be a timing-bug fix that recovered a narrow class of
signals at the signal-timing boundary. Not bank-worthy without understanding what the
specific timing error was and whether it is relevant to pancetta's sync pipeline.
Noted for monitoring.

### ta2ldv/ft8-ft4-decoder (pure-Python FT8 from scratch)

GitHub repository ta2ldv/ft8-ft4-decoder: pure-Python FT8/FT4 decoder for QO-100
WebSDR recordings. Implements Costas sync search, GFSK demodulation with soft LLRs,
LDPC(174,91) BP, CRC-14. No new decoder algorithm vs standard max-log + BP pipeline.
No sensitivity benchmarks found. Not bank-worthy.

### arXiv:2511.12108 (Guessing Decoding of Short Blocklength Codes, Nov 2025)

Comparison of GRAND and GCD (Guessing Code Decoder) families. GRAND is already a
documented dead-end for FT8 (hb-260: LDPC(174,91) rate 0.52 is far outside GRAND's
tractable guessing regime). The GCD contributions are code-agnostic theory (saddle-point
approximations for average query counts; ML-reaching stopping criteria). No FT8-specific
gain. Not bank-worthy.

### JTDX_contest SuperFox: CRC-aided successive-cancellation list decoding (experimental)

CE3TSK's fork includes an experimental "SuperFox" mode that uses CRC-aided successive-
cancellation list decoding for FT8 Fox expedition mode (not regular FT8). This is marked
experimental in the fork and has no published sensitivity measurement. pancetta already
implements Fox mode (PAN-386). This technique is noted for future follow-up if the
SuperFox feature matures; not bank-worthy at this time.
