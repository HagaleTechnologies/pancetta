## Ranked candidates

### Rank 1 — WSJT-X 3.3.0-beta4: AP a8 /R and /P DX call expansion (new hb-271 item)

**Technique:** WSJT-X 3.3.0-beta4 (released 2026-10-22) adds compound callsigns with /R
and /P suffixes to the AP a8 candidate list for FT8 decoding. Previously, a standard
call with a /P (portable) or /R (rover) suffix received a reduced or non-standard AP
candidate set; beta4 gives such calls the full a8 candidate set — the same 206-template
cross-correlation sweep that a plain callsign gets. The suffix is stripped before
standard AP template generation, so the first 206 candidates use the bare form; the
compound form is also tried.

**Primary source:** mfsk-core GitHub issue #694 ("WSJT-X v3.3.0-beta3/beta4 audit vs
beta2: RR73 sent as acknowledgment, /R /P AP candidates"; jl1nie/mfsk-core, 2026-10-25).
The issue performs a code-level audit of WSJT-X 3.3.0-beta4 against beta2 and documents
the AP a8 change. The WSJT-X GitHub releases page confirms v3.3.0-beta4 published
2026-10-22 with the fix "include /R and /P DX calls in the a8 candidate list." A
companion fix adds /R and /P handling to Q65.

**Measured evidence:** None (no A/B decode-rate measurement found for the /R /P AP
expansion specifically; release notes frame it as a correctness fix rather than a
sensitivity improvement). The fraction of FT8 QSOs using /P or /R on HF bands is small
but non-zero; VHF/UHF contesting and DXpeditions (where /P is common) would see the
largest benefit.

**Also in beta4:** RR73 is now packed as a "acknowledgment" message type rather than a
standard message. This is a protocol-level change with AP-lock implications: an AP lock
on RR73 may not match older senders' packing. This is distinct from the AP candidate
change and affects pancetta's AP wiring for the RR73 phase of a QSO.

**Applicability to pancetta:**
- pancetta's AP mechanism is in `pancetta-ft8/src/ap.rs` and `decoder.rs`.
  `pancetta-ft8/src/pack.rs` handles callsign packing; compound callsigns (`/P`, `/R`)
  follow type-3 (non-standard) or type-1/type-2 encoding depending on the 77-bit pack.
- hb-219 already graduated the `/R` → `/P` renderer fix (2026-06-05 Batch 35). That
  fix was cosmetic (display/logging). The beta4 change is different: it feeds /P and /R
  forms into the AP a8 *template generator*, which requires the *decoder* to try
  correlated decodes for compound-callsign partners. This is a new decode-path change.
- The AP a8 mechanism (`enumerate_a8_expected_texts` in `pancetta-ft8/src/ap.rs`) passes
  `dx_call` unchanged into every template format string, so compound-call templates
  (`CALL/P`, `CALL/R`) are already generated for any partner decoded with a compound
  callsign. `pack28` in the same module handles `/P`/`/R` suffixes correctly (lines 99–107).
  **Pancetta already handles the WSJT-X beta4 change by design; no extension is needed.**
  See hb-275 status below.
- Impact estimate: small (few percent of HF traffic). May be higher at VHF/UHF contest
  events where /P and /R are common and the recall gap from missing AP templates is
  real. License: none (mechanism is novel only in being ported to pancetta).

### WSJT-X 3.2.0 GA — never shipped; development at 3.3.0-beta4

**Key finding:** WSJT-X 3.2.0 apparently never reached a GA release. The WSJT-X GitHub
releases page lists v3.2.0-rc1 as the last rc1-tagged build; the next official release
after rc1 is v3.3.0-beta1 (released 2026-10-08). The sequence was:
3.0.0 GA (2026-04-06) → 3.2.0-rc1 → 3.3.0-beta1 (Oct 8) → beta2 → beta3 → **beta4
(Oct 22)**.

3.3.0-beta1 changes (mfsk-core issue #642 audit):
- FT8 code moved verbatim into a new PCM decoder engine API (no decoder change).
- Q65 retry-first-candidate quirk from rc1 fixed (rc1 zeroed `nqf` on entry; beta1
  sets the retry value from `nqf` first).
- Other changes: slow JT9, JT65, Q65, FST4/FST4W migrated to new PCM engine. JTTY
  mode Contest/FT8 chooser, per-message SNR, PSKReporter decode reporting.

3.3.0-beta4 changes (mfsk-core issue #694 audit, confirmed in GitHub releases):
- **FT8 AP**: /R and /P DX calls added to AP a8 candidate list (→ hb-275 draft above).
- **RR73 packing**: RR73 now packed as an "acknowledgment" type. AP-lock implications
  for older sender compatibility.
- **Q65**: /R and /P handling added to Q65 as well.

**Impact on hb-271:** hb-271 ("WSJT-X 3.2.0-rc1 decoder techniques") should be
updated to reflect that 3.2.0 GA never shipped and that the active development line is
3.3.0. The ablation measurements from mfsk-core issues #435 and #447 (AP llrc +0.36 dB,

**Uwe Risse (DG2YCB) left the core WSJT-X team in February 2026:** Confirmed in the

### hb-269 (RBE) construction procedure — confirmed applicable to non-5G LDPC codes

**Update:** The arXiv:2608.09560 paper ("Row-Boosted Ensemble Belief Propagation for
Short LDPC Codes", Bezner, Krieg, ten Brink) is now accessible via web snippets and a
Pith review summary. Key confirmed details for the probe plan:

- **Method:** RBE creates decoder ensemble diversity by boosting selected rows of the
  parity-check matrix H across ensemble members. This differs from aSCED (hb-262; coset
  ensemble members that change the active set of parity checks) and from hb-270 (SECS,
  which soft-combines decoder outputs and re-runs OSD). RBE preserves the full H matrix
  and the decoder kernel; it only scales selected row LLR contributions.
- **Key result:** 5G NR BG1 (144,96) at Eb/N0 = 4.0 dB: RBE-32 lowers FER from
  1.6×10⁻² (single BP) to 1.6×10⁻³ (10× improvement). The paper explicitly says
  "gains transfer across 5G NR block lengths and rates, **to non-5G short LDPC codes**,
  and across flooding and layered schedules." This is the key phrase that unblocks the
  LDPC(174,91) probe — the paper's own authors claim transferability to non-5G codes.
- **Pith caveat:** The row-selection corpus and the FER evaluation are not shown to be
  disjoint, so the 10× headline may be overstated. Not a blocker for a probe, but
  calibrate on a separate design corpus.
- **Ensemble size for probe:** K=32 is the paper's headline; a K=8 probe is cheaper
  and sufficient to confirm the mechanism before committing to K=32. Compare vs.
  aSCED-32 if a Rust aSCED is available.
- **License:** arXiv preprint (cs.IT, cc-by-nc-sa typically for arXiv); GPL or patent
  constraints not identified. Code: the kit-cel/RBE or kit-cel/aSCED repos may have
  reference implementations — check before implementing.

**Action for hb-269:** The construction procedure is no longer DNS-blocked. Read
§III-C–III-D of arXiv:2608.09560 directly (or via Semantic Scholar) to confirm the
row-selection algorithm and the ensemble vote rule. The probe is unblocked pending that
read. De-prioritize slightly vs. hb-273 (gated OSD-3, +0.35 dB confirmed) and the
hb-271 AP llrc item (+0.36 dB confirmed); but RBE's wall-clock cost per-ensemble-member
is low relative to OSD, making it a potentially high-throughput gain.

### arXiv:2509.25580 false-convergence detector — NMS-specific details confirmed

From the available HTML rendering, the paper's "undetected decoding error" (UDE) model
uses iteration distances (per-iteration LLR trajectories) from NMS BP to identify
likely false positives. This confirms the model is NMS-specific (trained on NMS
trajectory distributions). The paper notes FER differences due to NMS false positives
are "more pronounced for BCH and RS codes than for LDPC codes" — weakening applicability
to FT8's LDPC(174,91) further. hb-274 remains low priority as filed in the Oct 19 scan.
No change to its status.

## Noted but not bank-worthy

### arXiv:2607.04045 — SOGRAND as LDPC check-node update (NOT bank-worthy; hb-260 scope)

"SOGRAND decoding of LDPC codes" (Duffy, Feng, Rapp, Médard; MIT; July 4, 2026; cs.IT).
Specializes SOGRAND's SISO computation to Single Parity Check codes as a check-node
update rule for LDPC BP, offering "two low-complexity, hardware-friendly check-node
update algorithms." Claims "similar or better performance than Gallager's sum-product
algorithm and norm-min-sum."

**Why not bank-worthy:** (1) Pancetta already uses sum-product BP (the standard
tanh check-node rule), which is the *optimal* SPC decoder — the same computation
SOGRAND specializes to. The claim "similar or better than sum-product" means SOGRAND-CN
offers at most equal performance to pancetta's existing check-node rule in the AWGN
regime. (2) The paper's motivation is hardware efficiency (lower-complexity check-node
update), not improved decoding performance; the "similar or better" wording reflects
this. (3) hb-260 documents the GRAND family as a DOCUMENTED-DEAD-END for FT8 (July
2026 batch 96 scan). Although SOGRAND-CN is structurally different from GRAND as an
outer decoder (it applies GRAND's SPC-SISO inside the LDPC graph rather than at the
block level), the performance conclusion is the same: no gain over SP-BP.

### arXiv:2608.14280 — LLM-assisted LDPC decoding (NOT applicable to FT8)

"LLM-Assisted LDPC Decoding via Syndrome-Verified Semantic Priors" (Park, Lyu, Choi,
Yang; Aug 14, 2026; eess.SP). Uses an LLM to propose character-level corrections to
decoded text, filters them through parity-check verification, and injects accepted
corrections as soft LLR updates for a subsequent BP pass. Reports 73% BER reduction
vs. conventional decoder at 2.0 dB.

**Why not applicable:** The payload is natural-language text (characters). FT8's
structured 77-bit message vocabulary (callsigns, grid squares, signal reports, contest
serials) is already handled by AP (arXiv:2509.25580 / hb-048 / hb-271 AP llrc), which
injects structured FT8-specific priors into BP. The LLM-LDPC paper's parity-verification
step is architecturally equivalent to pancetta's existing AP mechanism; its LLM replaces
the structured AP template generator. No gain available over AP for FT8's fixed
vocabulary. Not bank-worthy.

### Kondor Weak Signal Modes Decoder (SDR++ plugin) — new product, no new technique

ReLLL's Kondor decoder (GitHub: ReLLL/kondor-weak-signal-modes-decoder) is a new/renamed
SDR++ and SDR++Brown plugin supporting FT8, FT4, WSPR, FST4, FST4W, JS8, Q65. Its
underlying FT8/FT4 decoder is MSHV's. Now supports standard SDR++ 1.2.0 in addition to
SDR++Brown. No new decoder technique. Noted for product landscape.

### WSJT-X 3.3.0-beta1 FT8 retry quirk (rc1 bug, now fixed)

mfsk-core issue #642 found that WSJT-X 3.2.0-rc1 appeared to retry only the first
candidate because the decode routine zeroed `nqf` on entry; beta1 fixed this by reading
`nqf` before the entry overwrite. The audit notes this affected the Q65 retry loop; the
FT8 decoder was moved verbatim to the new engine without the retry loop change. **This
is not a new technique** — it is a bug fix in rc1's Q65 path. No bank-worthy item.
