## Noted but not bank-worthy

### arXiv:2609.12389 — p-bit annealing LDPC decoding (Sep 11, 2026)

**Technique**: "Error-Rate Reduction in LDPC Decoding via Bit-Aligned Temporal
Reinforcement in Parallel Probabilistic-Bit Dynamics." Onizawa and Hanyu (Tohoku
University) study random-regular (3,6) LDPC decoding using Jacobi-type p-bit
annealing with stochastic partial activation. The core contribution is an additive
"temporal reinforcement" rule that stores each bit's saturated-state response and
reuses it as a prior before the next stochastic readout — a form of memory-enhanced
annealing. Claims BER reductions of 33.5%, 74.8%, and 81.8% relative to memoryless
probabilistic simulated annealing (PSA) for codes of block lengths 96, 192, and
288 respectively.

**Why not bank-worthy**:
1. **Hardware-motivated technique**: p-bits are probabilistic hardware units —
   stochastic bistable elements implemented in spintronic or CMOS circuits. The
   paper's context is a hardware accelerator paradigm and no software implementation
   is validated; the underlying stochastic activation and Jacobi update are in
   principle simulable, but the paper makes no efficiency claim for software. Even
   if simulated, rejection reasons 2 and 3 below apply independently.
2. **Weak comparison baseline**: gains are measured relative to memoryless PSA, not
   vs sum-product BP or OSD. PSA is far below pancetta's current decoder stack
   (SP-BP, 100 iterations, OSD). No comparison against BP or near-ML decoding
   is provided.
3. **Wrong code family**: tests use random-regular (3,6) LDPC codes — not the
   optimized, irregular LDPC(174,91) used in FT8. The paper makes no claim about
   performance on optimized or irregular LDPC codes.
4. **Block lengths**: tested at 96, 192, 288 — FT8's 174-bit code falls in this
   range, but the architecture constraint (1 above) makes this moot.

Source: arXiv:2609.12389, Naoya Onizawa and Takahiro Hanyu (RIEC, Tohoku
University), submitted 2026-09-11. URL: https://arxiv.org/abs/2609.12389

### arXiv:2609.06427 — LQ8 digital mode family (Sep 2026)

**Technique**: "The LQ Digital Mode Family: Protocol Architecture and Reference
Specification for Weak-Signal Communications." Introduces LQ8 (and the LQ mode
family), an open-source weak-signal amateur radio digital mode that completes
structured two-way contacts in 4 transmissions (60 s total), a 1.50× speedup over
canonical 6-transmission FT8 exchanges (90 s) and 1.25× over 5-transmission RR73
exchanges (75 s), while preserving full Maidenhead grid locator, signal report,
and acknowledgment exchange. Uses the same LDPC(174,91) + CRC-14 FEC as FT8,
with continuous-phase 8-GFSK modulation; claims -21.0 dB SNR sensitivity.

**Why not bank-worthy**:
- This is a protocol-architecture paper, not a decoder-improvement paper. LQ8 uses
  the same LDPC(174,91) decoder as FT8 and achieves the same -21.0 dB sensitivity.
  No new LDPC algorithm is introduced.
- The improvement is in QSO-completion latency (4-step vs 6-step protocol), not
  in decoding sensitivity or LDPC performance.
- Potentially relevant to pancetta's multi-mode roadmap (FT8/FT4/FT2 are already
  in-tree), but not to the decoder-research hypothesis bank.

Source: arXiv:2609.06427, submitted September 2026. URL: https://arxiv.org/abs/2609.06427

### Decodium 4.0 Core Shannon — benchmark showing 27–66% more decodes than other apps

**Context**: The ft2.it benchmark compares four FT8 decoders over four rounds
spanning 70 minutes on a shared antenna feed, with Decodium winning every round by
27–66% depending on the competitor app. Separately, the Decodium 4.0 documentation
claims "+1.3 dB of sensitivity improvement over plain min-sum," a decode chain
"~16× faster," and a fix for "a sign bug in Decodium's min-sum branch that was
silently costing decodes in FT8, FT4, and FT2."

**Why not bank-worthy**:
1. **Algorithm is weaker than pancetta's**: The Decodium Core Shannon decoder uses
   Normalized Min-Sum (NMS) with max 20 iterations. Pancetta uses sum-product BP
   with 100 iterations + OSD at depth 0 (production default; depth 1 is an
   available experimental configuration, not deployed). SP-BP is provably better
   than NMS at
   equal iteration count; the "+1.3 dB" gain is NMS-fixed vs NMS-broken, not NMS
   vs SP-BP, and no matched-corpus comparison exists to bound pancetta's advantage
   from this data.
2. **GPL v3 license**: The Decodium 4.0 Core Shannon source is published on GitHub
   (iu8lmc/Decodium-4.0-Core-Shannon) under GPL v3. The clean-room spec firewall
   applies; pancetta cannot read the source. The technique (NMS normalization fix)
   is described in the documentation at a level sufficient to characterize it without
   reading the GPL source, and is not novel.
3. **Benchmark context**: The 27–66% advantage is measured on-air against WSJT-X
   mainline and JTDX. Per `research/specs/spec-wsjtx-mainline-osd174.md:263-267`,
   WSJT-X uses standard log-domain SP-BP (tanh/atanh); JTDX descends from the same
   codebase. Both use OSD (ndepth=2/3 for WSJT-X, ndepth=2 for JTDX). Decodium's
   fixed NMS apparently outperforming SP-BP competitors in this benchmark is not
   explained by the published documentation alone (possible confounds include AP
   levels, multi-pass passes, and receiver pipeline differences). The NMS normalization
   fix is not applicable to pancetta regardless, since pancetta already uses SP-BP —
   the fix corrects a bug in NMS arithmetic that does not exist in SP-BP code.
4. **Sign bug is in Decodium's own code, not FT8**: The sign bug was a Decodium-
   internal implementation error in their min-sum branch. There is no corresponding
   known sign bug in pancetta's sum-product decoder or in the WSJT-X reference.

Source: ft2.it benchmark article (proxy-blocked; content obtained via search
snippets); Decodium 4.0 User Manual v1.0.498 (ft2.it/manual/decodium4_manual_en.html);
GitHub: github.com/iu8lmc/Decodium-4.0-Core-Shannon
