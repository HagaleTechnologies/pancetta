# Operating modes

## FT4 mode (7.5s digital mode, station-wide, startup-selected)

`pancetta-core/src/slot.rs`, `pancetta-ft8/src/protocol.rs`, `pancetta-config/src/rig.rs`, `pancetta/src/coordinator/{mod.rs,dsp.rs,ft8.rs,tx.rs}`, `pancetta-qso/src/qso_manager.rs`, `pancetta-core/src/types/band.rs`, `pancetta-tui/src/{config.rs,app.rs,ui/mod.rs}`: operate **FT4** — the faster (7.5s T/R, 4-GFSK) FT8 sibling — as a **single active mode the operator selects at startup** (`[rig] mode = "FT8" | "FT4" | "FT2"`, default FT8; the whole station runs that mode, WSJT-X-style). **The codec already existed** (`ProtocolParams::ft4()` + round-trip tests); this was an *integration* of timing + mode-stamping, NOT a new codec. **Hard regression invariant: mode=FT8 is byte-identical to before** — everything resolves to today's exact constants. Pieces: (1) **period-parameterized slot timing** — every `pancetta-core::slot` fn gained a `_with_period(…, slot_ns)` variant; the originals are FT8 (`SLOT_NS`=15e9) wrappers, so the 22 legacy slot tests are unchanged. (2) **`active_slot_ns` + `active_decode_phase_ns` atomics** + a pure `derive_dsp_timing(&ProtocolParams) -> DspTiming { window_samples, decode_phase, overlap_samples, slot_ns }` (FT8 → 151_680/13s/180_000/15e9; FT4 → 60_480/6.5s/90_000/7.5e9), threaded into `dsp.rs` (window/decode-phase/overlap) and `ft8.rs` parity-stamping (`SlotParity::of_with_period` with the slot start recovered as `window_received − decode_phase`, NOT the old literal 13s — the literal would invert FT4 parity → on-air collisions). (3) **TX scheduler** `schedule_tx(… slot_ns)` + `resolve_required_parity` honor the active period (pre-PTT lead fits the 7.5s slot). (4) **Decoder actually runs FT4:** the shared `Ft8Config.protocol` is seeded from `[rig].mode` (not just the timing atomics — else the decoder would demod FT8 geometry against FT4 audio). (5) **Mode stamped** into `QsoManagerConfig.active_mode` → `QsoMetadata.mode` → ADIF `MODE:FT4`, and the decode views → a cyan title-bar **mode chip** (hidden for FT8). (6) **FT4 per-band dial frequencies** (`Band::ft4_frequency()` + `dial_for(is_ft4)`; autonomous band-hop `ChangeBand` overrides to the FT4 sub-band in FT4 mode). Residual-decode path (`decoder.rs::codeword_to_symbols`, FT8-hardcoded) is **never reached for production FT4** (single-pass; the path is multi-pass-only) — proven, documented, not parameterized. **Scope / non-goals (v1):** no simultaneous FT8+FT4 decode, no FT4 Fox/Hound. ~~single active mode selected at startup (runtime mode-toggle = v2)~~ and ~~manual TUI `=`/`-` band-change dial stays FT8-table (active mode not threaded to that TUI path — TODO)~~ — **both shipped, see the runtime mode-switch section below.** Also flagged to dispensa (Q-0009): the rig-api `stateSnapshot` needs a `mode` field for panino to show FT4. Spec: `docs/superpowers/specs/2026-06-29-ft4-mode-design.md`; plan: `docs/superpowers/plans/2026-06-29-ft4-mode.md`.

## Runtime FT8/FT4/FT2 mode switch (Shift+M)

`pancetta/src/coordinator/mod.rs::{try_switch_operating_mode,ModeSwitchError}`, `coordinator/{tui_relay.rs,dsp.rs,ft8.rs,tx.rs,qso.rs}`, `pancetta-qso/src/qso_manager.rs::set_active_mode`, `pancetta-tui/src/app.rs::apply_band_selection`: the FT4-mode landing above made `active_mode` write-once (startup-only); this makes it a **live** switch. `active_protocol_mode`/`active_slot_ns`/`active_decode_phase_ns` are now atomics that the DSP window/decode-phase, `ft8.rs` parity-stamping, and the TX scheduler all re-read per iteration/slot instead of capturing once at startup. `try_switch_operating_mode` is the single gate: it takes a **synchronous** read lock on `active_tx_qsos` (zero `.await` in the critical section, mirroring the auto-repark invariant) — refuses with `ModeSwitchError::QsosActive(n)` if any QSO is non-terminal, `QsoSetUnavailable` on a poisoned active-set lock, `ConfigLockBusy` on a contended/poisoned `Ft8Config` lock — and only mutates the shared `Ft8Config.protocol` + the three atomics on success, so a failed switch never leaves consumers disagreeing about the active protocol. This gate is airtight against an already-registered QSO (its insert needs a write lock on the same set) but has a narrow, low-severity residual window against a QSO still being *created* concurrently (registration happens asynchronously, slightly after creation, e.g. autonomous `respond_to_cq`/always-answer-callers) — a bounded gap, not a full end-to-end closure of the race. Wired to **Shift+M** in the TUI (`tui_relay.rs`), which also calls `QsoManager::set_active_mode` so subsequently-opened QSOs stamp the new mode into ADIF. Manual TUI `=`/`-` band-change (`apply_band_selection`) is now mode-aware (reads the live mode, closing the gap noted in the FT4-mode section above). FT2 is unaffected — still falls back to FT8 on non-`ft2`-feature builds, pre-existing behavior, not changed by this work. Regression-guarded end-to-end in `pancetta/tests/coord_sim.rs` (`mode_switch_*` scenarios): refused-while-active (real `active_tx_qsos` populated via the real populater), succeeds-when-idle + next QSO stamps the new mode, and a byte-identical-if-never-touched invariant mirroring `ptt_keys_for_scheduled_qso`.

## FT8 Hound mode (DXpedition chaser, manual v1)

`pancetta-qso/src/{qso_manager.rs,states.rs,adif.rs}`, `pancetta-config/src/hound.rs`, `pancetta/src/coordinator/qso.rs`, `pancetta-tui/src/{tui_runner.rs,ui/qso_status.rs}`: work a DXpedition Fox using the Hound procedure — **call the Fox low (300–900 Hz audio), QSY up (1000–2700 Hz) on the Fox's report + send R-report there, complete on the Fox's RR73, log it flagged.** It's an FT8 *operating procedure* (same 8-GFSK modulation/encoder/decoder — NO `protocol.rs` change; mode stays `FT8`). **Operator-engaged via `Shift+H`** on a selected DX-Hunter row (lowercase `h` is StopTx) → `TuiCommand::EngageHound` → `QsoMessage::EngageHound` (TX-policy-gated + half-duplex parity-admit, exactly like `CallStation`; cross-window picks defer into `PendingManualCalls` carrying the Hound flag) → `QsoManager::engage_hound` opens a manual `RespondingToCq` QSO. **Core new concept — Tx≠Rx:** a Hound transmits on a different offset than where it hears the Fox, so `QsoMetadata` gains `partner_freq: Option<f64>` (the Fox's RX offset) separate from `frequency` (our TX offset); `is_message_relevant` keys on `partner_freq.unwrap_or(frequency)` — **`None` (every non-Hound QSO) is byte-identical to before** (regression-guarded). On the `(RespondingToCq, SignalReport)` transition, if `hound && !hound_qsyed` the engine QSYs (mutates `metadata.frequency` + per-cycle `qso_frequency` + the next `SendingReport` state's frequency together, mirroring the stuck-hop) into the response region — **fires once, independent of `TxFreqMode`** — so the emitted `ReportAck` rides the high offset. Offsets are deterministic per-Fox via `hound_offset_for(callsign, lo, hi)` (FNV hash → 5 Hz snap; no RNG; spreads concurrent Hounds). Decoder bin-hint (`active_qso_freq_hz`) tracks `partner_freq` for Hound QSOs. ADIF: flagged via `COMMENT` "HOUND" + an `APP_PANCETTA_HOUND` field (MODE/SUBMODE stay FT8). TUI shows a `[HOUND]` badge (threaded via `ActiveQsoSnapshotItem.hound`). Scope: **manual-initiated, Hound-only** (running *as* the Fox is the next build; multi-mode `mode`-field on rig-api deferred to FT4). Config `[hound]` (call/response audio regions). Engine proven by `pancetta-qso` engine-sim tests + a rig-level `coord_sim` scenario (`hound_engage_keys_low_then_qsys_high_on_report`: PTT keys low → Fox report → keys high → RR73 → Completed). Spec: `docs/superpowers/specs/2026-06-27-hound-mode-design.md`; plan: `docs/superpowers/plans/2026-06-27-hound-mode.md`.
