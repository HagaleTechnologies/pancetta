# QSO engine

## Manual vs. automated calling semantics

`pancetta-qso/src/qso_manager.rs`, `pancetta-qso/src/autonomous.rs`: A `CallInitiation::{Manual,Auto}` flag on each QSO (in `QsoMetadata`) drives two policy differences. **Manual calls** (operator Space/CallStation → `respond_to_cq_manual`) bypass the self-duplicate gate (the operator explicitly chose to work/re-work the DX) and **keep-call every TX slot** until the DX answers or a watchdog fires. The watchdog (`check_timeouts_at`) retires a manual `RespondingToCq` QSO after **5 minutes OR 25 calls, whichever first** (`TimeoutConfig::{manual_call_watchdog_minutes, manual_call_max_calls}`, defaults 5/25 — #43 raised the cap from 10 so the 5-minute *time* bound governs; the cap is a runaway backstop, applies only to initial-call states — `CallingCq`/`RespondingToCq`; `SendingReport` and `WaitingForReport` are exempt from the call-count cap once the DX has engaged, governed only by the time bound). Keep-calling is driven by `rearm_manual_calls_at` in the QSO manager's 5s timeout loop, which re-emits the rung actually in flight per state (`Cq`, `CqResponse`, `SignalReport`, or `ReportAck`, matching whichever ladder step the QSO is stalled at — see the 2026-07-18 deep review's SM-F4 for the `WaitingForReport` re-send arm added in Batch 4) — the coordinator's existing QSO event loop forwards it as a `TransmitRequest` with the latched `tx_parity`. Since Batch 4, `RespondingToCq`/`SendingReport` also re-arm for **Auto** QSOs, bounded by a small hardcoded `AUTO_RESEND_MAX_CALLS` (not the manual watchdog's 25/5-min bound) so an autonomous pounce gets one bounded resend instead of dying silently on the first missed reply. **Automated calls** keep the duplicate gate AND additionally yield to a busy DX: the autonomous operator tracks callsigns seen in a non-CQ third-party exchange (report/RR73/73 not directed at us) in `recently_in_qso`, and suppresses an auto-response to any such station that CQs again within `AutonomousConfig::dx_busy_window_secs` (default 90s). Both shipped 2026-06-13 in response to an operator duplicate-QSO bug.

## Manual CQ as a real `CallingCq` QSO

`pancetta-qso/src/qso_manager.rs::start_cq_manual`, `pancetta/src/coordinator/{tui_relay.rs,qso.rs}`, `QsoMessage::{StartCq,StopCq}`: pressing **`c`** no longer runs a separate text-only CQ-repeat loop. The TUI's `StartCq` is routed to the QSO component, which calls `start_cq_manual` to create a tracked **manual** `CallingCq` QSO. That QSO **owns the CQ transmission** (single TX source per slot — no double-TX): it emits a `StateChanged` (Idle→CallingCq, so the coordinator keys it into `active_tx_qsos` and the TX worker will key PTT for it) and an opening `Cq` `MessageToSend`, then `rearm_manual_calls_at` re-emits one `Cq` per FT8 slot (its `CallingCq` arm, gated to ~1/slot via `last_call_at`) bounded by the **same manual watchdog** (5 min / 25 calls; `check_timeouts_at` covers `CallingCq` too). When a station answers, the existing `CallingCq + CqResponse → WaitingForReport` arm fires and the `CallInitiation::Manual`-gated auto-reply emitter sequences our report → RR73 through to `Completed` + `QsoCompleted` (ADIF log), latching the caller's grid. `tx_parity` is latched once at creation via `latch_cq_parity_if_none` (a concrete parity, not `None` — the "nearest next slot" pick is resolved exactly once and held for the QSO's life; see the 2026-07-18 deep review's SM-F2/TX-F2 finding for why the equivalent responder-path gap — `respond_to_cq_with`/`respond_to_caller` answering with no observed `dx_parity` — was a real bug fixed in Batch 2 of `docs/qso-tx-deep-review-2026-07-18.md`). If multiple stations answer, the first valid `CqResponse` advances the single QSO; later answers no longer match (state moved past `CallingCq`) — one QSO per CQ. **`s`** (StopCq) sends `QsoMessage::StopCq`, which cancels only QSOs still in `CallingCq` (an already-answered exchange is left to finish); TX-policy-away-from-Full, Shift+Q (CancelAllQsos), `g`→Disabled, and F8 also cancel it. Shipped 2026-06-15, closing the "we can't actually run a CQ-initiated QSO" gap.

## Auto-resend 73 after manual completion (item-2-auto-73)

`pancetta/src/coordinator/qso.rs`: when a station we JUST completed a **manual** QSO with keeps re-sending us `RR73`/`RRR` (they didn't copy our 73), the coordinator auto-re-sends our 73 — bounded so a stuck DX can never make us TX forever. On `QsoEvent::QsoCompleted` with `metadata.initiated_by == Manual`, the QSO component stashes `(uppercased callsign → {completed_at, freq, dx_parity, resends, last_resend_at})` in a per-task `RecentManualCompletions` map (autonomous completions are NOT stashed). In the decode loop, a directed-at-us `FinalConfirmation` (RR73/RRR with `to_station == our call`) from a stashed callsign triggers `maybe_auto_resend_73`, which sends our 73 via the same `respond_to_caller(SeventyThree)` path the Callers/Space close uses (the resulting Completed QSO rides the drop-stale-TX grace window — the 73 frame goes out then drops). **Bounds: 3-minute window, max 3 resends per completed QSO, at most one per ~15 s slot.** Gates: respects the global `TxPolicy` (`allows_any_tx()` — RESPOND-ONLY allows, DISABLED blocks), manual-only (enforced at populate time), and skips if a live QSO with the station is already active. The counter is incremented under the map lock before the send so two decodes racing in one slot can't both fire.

## QSO sender verification

The QSO state machine (`pancetta-qso/src/qso_manager.rs::determine_state_transition` and `is_message_relevant`) verifies `from_station == expected DX callsign` on every state-advance. Mismatches are logged at `warn!` level (`target: "qso.security"`), discarded, and surfaced as retained Warn diagnostics in the TUI's Shift+D overlay. Frequency tolerance is 15 Hz for initial/ambiguous matching; an already-established QSO matches at 100 Hz (B15) since the partner's decoded offset can drift slightly across a multi-minute exchange, and a Hound QSO matches on `partner_freq` instead of the QSO's own latched frequency. The autonomous responder (`autonomous.rs`) tracks per-callsign response timestamps in `recently_responded_to` and skips CQs from callsigns it responded to within the last 60s. Both defenses landed 2026-04-29 in response to Security Review C-1 and I-1; see `docs/security-review-2026-04-29.md`.

### Split-TX drift relatch (PAN-12)

`partner_freq` is the generic location where we expect to hear the DX, not a Hound/Fox discriminator. It is set both for genuine Hound/Fox and for ordinary manual QSOs whose TX offset diverges because of an operator hold, collision nudge, or `[300, 2700]` clamp. `metadata.hound` alone identifies the protocol procedure and retains the drift-confirm carve-out.

For non-Hound split-TX, the two-strike drift mechanism measures from `partner_freq`, exactly as `is_message_relevant` does, and confirmation relatches only `partner_freq`. Our TX offset remains unchanged. Measuring from our TX offset, as issue #245 initially suggested, would falsely classify a healthy held-offset or collision-nudged QSO whenever the DX transmits at its expected partner frequency. The anti-spoof posture is unchanged: sender identity, two consistent sightings at least five seconds apart, and the RX plausibility bounds still gate every relatch.

### Operator-visible rejection reasons (2026-07-31)

Sender-verification rejection is represented by typed `RejectionReason` data and carried across the crate boundary as `QsoEvent::MessageRejected`. This deliberately preserves the return types and accept/reject behavior of the safety-critical `is_message_relevant` and `determine_state_transition` functions: the coordinator, which owns the `MessageBus`, translates the event into a `ComponentId::Qso`, `target: "qso.security"`, Warn-level `DiagnosticEvent` with the rejected sender attached as its callsign. The same full-fidelity helper covers self-call refusals already inside the coordinator while retaining their existing logs and ephemeral status updates.

`is_message_relevant` can reject a structurally matching frame before `determine_state_transition` runs, so those routing-stage rejections must emit independently; relying only on the transition guards leaves classic impostor frames silent. Emission is intentionally curated: a diagnostic is produced only when a frame is addressed to us but the sender is not the QSO partner (or for another explicit security refusal). Unrelated band traffic, frequency-gate misses, and inactive-QSO skips remain silent so the retained 500-event TUI ring is not flooded. Autonomous skip/pounce suppression sites remain a separate follow-up rather than being reclassified as sender-verification failures.

## Compound-callsign equivalence (catalog C18 / peer D4)

`pancetta-qso/src/exchange.rs::{base_callsign,callsigns_match}`, applied in `qso_manager.rs::{is_us,is_partner}`: a station may sign a compound call (`EA8/G8BCG`, `G8BCG/P`, `K1ABC/R`, `VK9/W1XYZ/MM`) and later in the SAME QSO sign its bare base (`G8BCG`), or vice versa — same operator. WSJT-X/JTDX stall here because sender-verification compares the *displayed* call to the latched partner; pancetta does not. `callsigns_match` treats two calls as the same station iff they are byte-identical (uppercased) OR share a `base_callsign` — the longest `/`-separated component that is callsign-shaped (≥3 chars, has a digit AND a letter), which picks the home call over a country prefix or a portable suffix. It is conservative: genuinely different calls (`K5ARH`/`K5ARG`, `G8BCG`/`G8BCH`) extract distinct bases and never match, so the sender-mismatch security tests still reject impostors. Every `from == DX` (`is_partner`) and `to == us` (`is_us`) check in `determine_state_transition` + `is_message_relevant` routes through it, so a mid-QSO compound↔base change no longer stalls. `validate_callsign` was widened to accept compound forms (valid base + short prefix/suffix tokens) so compound frames parse instead of erroring out of the pipeline. The logged `their_callsign` is upgraded to the most-complete (longest matching) form seen — the compound carries DX/portable info. Tests: `pancetta-qso/tests/adversarial_compound_calls.rs`.

## hb-062 FP filter: fixed dead-code init-order bug (2026-07-12)

`pancetta/src/coordinator/mod.rs`/`ft8.rs`/`autonomous.rs`: the production `CallsignContinuityFilter` (built in `run()`, after the cqdx-bridge async startup) was silently inert for the life of the process. `start_pipeline()` spawns the FT8 decode thread *before* the filter is built, and the thread captured `self.fp_filter.clone()` as a plain `Option<Arc<...>>` snapshot — always `None` at that point, so the `if let Some(ref filter) = fp_filter { decoded_messages.retain(...) }` branch never ran and hb-062's defense against OSD-fabricated decodes never fired in production (same bug class as the earlier blank-TX-placement-instrument fix). Unlike that fix, the filter's construction couldn't just be moved earlier — it depends on the cqdx bridge's async startup, which itself runs after `start_pipeline()` for good reason (pipeline start shouldn't block on network I/O). Fix: `fp_filter` is now `Arc<RwLock<Option<Arc<CallsignContinuityFilter>>>>`, matching the existing `active_qso_ap`/`active_qso_freq_hz` live-read pattern in the same file — all three consumers (the FT8 decode loop, the hb-237 cross-sequence cache gate, and the autonomous operator's TX-side gate in `autonomous.rs`) now read a fresh snapshot each window/call instead of a value captured once at spawn time. Also fixed: the filter's own `info!`/`warn!` startup diagnostics used `target: "fp_filter"`, which doesn't start with `"pancetta"` and so fell outside the default `EnvFilter` directive (`pancetta={level},warn` in `main.rs::init_logging`) — `info!` was silently dropped at the default log level even though the code ran on every startup. Renamed to `target: "pancetta::fp_filter"`. Regression test: `coordinator::tests::fp_filter_write_is_visible_through_a_clone_taken_before_the_write` (`mod.rs`) pins that a clone taken before the filter is built still observes a later write through the shared lock.

**Broader audit flagged, not fixed this pass**: the same `target: "..."` bare-string pattern (not `"pancetta"`-prefixed) is used by ~40 other `info!`/`debug!`/`warn!` call sites across the coordinator, `pancetta-qso`, `pancetta-dx`, `pancetta-agent`, and `pancetta-config` crates (e.g. `"qso.security"`, `"tx.policy"`, `"agent.tx"`, `"rig.split"`, `"dx.qrz"`, `"gateway"`) — each has the same invisible-by-default gap for `info!`/`debug!` severity. `warn!`/`error!` calls on these targets are unaffected (already visible at the default level). Not fixed here because several of these exact string literals are used in TWO unrelated places in the same files: as a tracing macro `target:` AND as a `DiagnosticEventRecord`/`ComponentMessage` struct field (an unrelated bus-panel label, confirmed via `pancetta-tui/src/app.rs:375`'s `DiagnosticEventRecord.target: &'static str`) — several are also in `pancetta/src/coordinator/tx.rs`, a TX-timing safety-critical file. A blind mechanical rename risks conflating the two or touching that file without careful per-site verification; needs a proper file-by-file pass, not a sweep, before being fixed.

## AP decoding eval mode: gate phantom AP decodes out of the QSO engine (2026-07-17)

`pancetta-config/src/decoder.rs` (`DecoderConfig::ap_eval_mode`), `pancetta/src/coordinator/ft8.rs` (`partition_ap_eval_decodes`): an operator live-diagnosed a "ghost caller" bug — the always-answer-callers path (#39) replied mid-QSO to stations that, per the operator's own review, never actually called. Root cause traced to AP (a priori) decoding: `pancetta-ft8`'s decoder deliberately biases the LDPC solver toward finding the operator's own callsign in a signal, so weak genuine calls decode — but the same bias can converge on pure noise and fabricate a plausible-looking "someone is calling us" message (the decoder module's own comment: "AP injection biases the LDPC solver toward our callsign, producing phantom messages... from noise"). The observed pattern matched: decodes of other stations calling a `/P`-suffixed variant of the operator's callsign at very weak SNR (-15 to -17 dB) — `/P` compounds are exactly the kind of near-miss a noise-biased solver would converge on, and `classify_caller_answer`'s compound-callsign matching (see "Compound-callsign equivalence" above) means a phantom `K5ARH/P` decode is recognized as addressed to the operator and answered. `DecodedMessage.ap_level` (0 = no AP, 1-4 = AP level used) was already tracked per-decode but never logged or surfaced, so it was impossible to confirm after the fact whether a specific past decode was AP-derived.

Two changes, both additive and default-preserving:
1. The `"FT8 decoded: ..."` log line now always includes `ap={ap_level}` — every decode's AP provenance is now visible in the logs going forward, independent of the eval-mode flag.
2. New `[decoder].ap_eval_mode` config flag (default `false`, so behavior is byte-identical to before this change unless explicitly enabled). When `true`, `partition_ap_eval_decodes` splits each window's decoded messages into (delivered, suppressed) immediately after the FP filter — before cross-slot-state, the TUI, the QSO engine, or the autonomous operator ever see them — routing every `ap_level > 0` decode into `suppressed`. Suppressed decodes are still logged in full (text, SNR, freq, ap_level) via a dedicated "AP eval-mode: decode suppressed" line, so the false-positive rate stays observable while under investigation, but they can never reach `classify_caller_answer` or trigger a reply. Non-AP decodes (`ap_level == 0`) are completely unaffected in both modes. This is a data-collection mode, not a permanent fix — intended for the operator to run for a while and gather evidence on the true AP false-positive rate before deciding whether to raise `MIN_AP_CONFIDENCE`, change the `ap_injection_survived` sanity check, or take some other permanent action in `pancetta-ft8`. Tests: `pancetta::coordinator::ft8::ap_eval_mode_tests` (4 cases — no-op when off, mixed-batch partitioning, all-non-AP, all-AP).

## QSO/TX deep-review remediation (2026-07-18) — 5 batches, all landed

Full findings + rationale: `docs/qso-tx-deep-review-2026-07-18.md`. QSO-engine-relevant fixes, in landing order:

- **Batch 1** (`6b2ceaf9`): closed the open double-PTT-for-73 bug. Root cause was the TX worker's Step-4c late pivot rewriting an in-flight frame's text to the freshest intent without consuming it, so the newer request that produced that intent keyed the identical text again a slot later. Fixed with a worker-local consume-once tombstone (`is_pivot_duplicate`, `coordinator/mod.rs`) plus a `resend_last_tx` stamping fix and the pivot's log target being made visible at the default log level (it was invisible, which is why prior tracing missed it).
- **Batch 2** (`584dd81a`): `respond_to_cq_with`/`respond_to_caller` now latch a provisional concrete `tx_parity` (via `latch_cq_parity_if_none`) instead of leaving it `None` forever when `dx_parity` is unknown (answering a cluster/DX-Hunter spot with no live decode yet) — the responder-side counterpart of the CQ-path BUG-1 fix. The first genuine decode from the latched partner refines the provisional parity to the true opposite-of-DX value. The TX coalescer and the autonomous multi-TX bundler now exclude (not silently coerce) a bundle stream whose parity disagrees with the bundle anchor, and `RespondToCaller` gained the same `admit_new_qso` half-duplex admission gate `StartQso`/`StartAutonomousQso`/`EngageHound` already had.
- **Batch 3**: frequency-allocator correctness (spectral axis mislabel, wall-clock-vs-decode-parity occupancy stamping, a scoring-floor bug, the dead own-frequency registry, and Tx=Rx de-confliction) — see `docs/DECISIONS/tx-scheduling.md`.
- **Batch 4**: the CQer role gained resilience to a caller repeating their grid after missing our `SignalReport` in `WaitingForReport` (a new `our_report`-latching regression arm, mirroring `SendingReport`'s own anti-jitter design); Auto QSOs in `RespondingToCq`/`SendingReport` get one small, safety-bounded resend instead of zero; and `QsoEvent::QsoFailed` is emitted at all three terminal producers (`cancel_qso`, `check_timeouts_at`, `supersede_active_qsos_for`), reviving the priority-scoring failure-backoff consumer that never received an event to act on.
- **Batch 5**: the operator's parked TX offset (`o` modal) now reaches the autonomous engine's Hold-mode branch; a timestamp-based guard closes a race where a duplicate RR73 decode could fire a second 73 before the first (from the same completion) cleared the TX scheduler's defer window; and the TX-placement instrument's spectral/decode-history feed now runs even when `autonomous.enabled = false` (only the actual TX decision/dispatch stays gated), so a manual-only operator sees a live instrument instead of a permanently blank one.

`docs/qso-state-machine-analysis.md` (2026-07-03) is superseded by the 2026-07-18 review for anything it also covers — its Symptom A/B and early-close-arm findings were already fixed at the time it was written; treat the 2026-07-18 review as authoritative for current gaps.

## Grace-window idempotent close (same-day follow-up to Batch 1, this batch)

Batch 1's `is_pivot_duplicate` tombstone (above) closed the double-PTT bug for a single in-flight frame, but left a second, distinct dedup gap: `respond_to_caller`'s **FIX 1** dispatch (`qso_manager.rs`, "if we already have an ACTIVE manual QSO...") only catches a re-call while a QSO is still active — once it reaches terminal `Completed`, FIX 1's `find_active_manual_qso_for` no longer matches it, so a subsequent close-step (`Rr73`/`SeventyThree`) reply for the same station builds a brand-new `QsoId`. Observed on-air: the operator pressed "send 73" 3 times in 8s trying to recover from a stuck exchange, producing 4 duplicate ADIF log entries for the same contact (each with its own real 73 keyed on the air). New `find_recently_completed_manual_qso_for` (delegating to an explicit-`now` `_at` variant, mirroring `check_timeouts_at`'s testability pattern) looks for a manual QSO with the same (callsign, band) that COMPLETED within `COMPLETED_QSO_REWORK_GRACE` (45s — deliberately the same value as `coordinator/qso.rs`'s drop-stale-TX `completed_tx_grace`, sourced from the one shared constant so the two windows can never drift apart). `respond_to_caller` now checks this whenever FIX 1 doesn't fire AND the requested step is a close step (`step_ladder_rank(step) >= Some(2)`): a hit re-keys the existing QSO's last frame via `resend_last_tx` and returns its existing id — no new QSO, no second `QsoCompleted`. A `Grid`/`Report`/`ReportAck` reply within the same grace window is left untouched (deliberate legitimate-rework path — e.g. working the same station again on a fresh exchange) and still opens a new QSO, matching `respond_to_cq_with`'s existing (unchanged) FIX 1 behavior for the `StartQso` path.

## Compound-callsign QSOs never transmit (PAN-17)

`pancetta-ft8/src/{encoder.rs,message.rs}`, `pancetta-qso/src/{qso_manager.rs,states.rs}`, `pancetta/src/coordinator/qso.rs`, `pancetta-tui/src/ui/mod.rs`: live-reproduced 2026-08-13 (YS/WE9G) — a QSO with a compound prefix/homecall callsign (`YS/WE9G`, `8G81PA`, `3E40CDW`, ...) queued and kept re-arming a TX every slot for the full 5-minute watchdog window but never actually keyed the radio. Root cause: `Ft8Encoder::encode_message` only ever tried the i3=1 standard path (`pack28`, a fixed 6-char mixed-radix scheme with no representation for an arbitrary compound prefix/homecall) and the i3=0/n3=0 free-text path (13-char cap, blown past by any real `<call> <call> <grid>` exchange) — it had zero equivalent of the i3=4 nonstandard-callsign hash-based encoding the *decoder* (`MessageParser::parse_nonstd_call`, `message.rs`) already implemented, so `encode_message` always returned `Err` for this whole class of callsign. Fix, two parts:

1. **Encoder**: `Ft8Encoder::try_encode_nonstandard` adds the i3=4 path (mirrors the decode-side bit layout exactly: n12(12) + n58(58) + iflip(1) + nrpt(2) + icq(1) + i3(3) = 77 bits), wired into `encode_message`'s fallback chain between the standard and free-text paths. One callsign is packed exactly into the 58-bit base-38 field (`pack58`, up to 11 chars, charset `" 0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZ/"` — new `message.rs::{pack58,hash12,HASH_CALL_CHARSET}`, `pub(crate)` so the encoder can reuse them); the pack28-failing callsign always wins that slot (never falls back to hashing the *intended* DX and exact-packing our own call instead, which would silently address the frame to a hash of garbage — e.g. the decoder's own `<...>` hash-miss placeholder). The other callsign is represented via a 12-bit hash (`hash12`, never fails — any string hashes, same as real FT8 traffic). The 2-bit `nrpt` report field only has room for 4 values (blank/RRR/RR73/73) — there is no bit budget left for a grid square or a numeric dB report once one callsign already needs the compound slot. A grid square (`extra_is_grid_locator`) is dropped (encoded blank) rather than failing the whole message — that still produces a valid, distinct "bare pairing" frame, and an FT8 QSO can complete without ever exchanging a grid with a compound-call station. A `looks_like_callsign` guard (real callsign shape — letters both before AND after the digit block, not just "has a digit and a letter somewhere" — see round 2 below) keeps this path from misfiring on arbitrary free text.
2. **QSO-engine watchdog**: a QSO whose DX callsign can never be represented in *either* wire format (invalid characters or >11 chars — not just "compound", genuinely unencodable) previously indistinguishable from "the DX never answered," consuming the full `manual_call_watchdog_minutes` window before self-retiring as a plain `Timeout`. `QsoManager::check_timeouts_at` now checks `callsign_is_wire_representable` (a local, dependency-free mirror of the encoder's hash-charset/length constraint — pancetta-qso only pulls in pancetta-ft8 optionally, for the `sim-hifi` harness, not at runtime) on the first watchdog pass for any active outbound-facing QSO, and retires it immediately with the new `QsoFailureReason::MessageUnencodable(String)` — encoding is a pure function of the callsign text, so there is nothing to gain by waiting. Surfaced distinctly in the TUI (`failure_reason_text` → "cannot transmit this message: ..."; `recent_qso_failure_color` → Red, same bucket as `ProtocolError`/`InvalidCallsign`) instead of reading like a bogus no-reply timeout.

Deliberately out of scope (round 1): how a QSO's `their_callsign` could end up as the literal decode-side placeholder `<...>` in the first place (a separate, upstream hash-table-miss propagation question); no change to `pack28` or the free-text path; no live/on-air re-verification (encoder-level round-trip tests plus the new watchdog unit tests are the evidence).

### Round 2 (Codex PR review #248, same day): TX-only was not a working QSO

Round 1 shipped an ENCODE-only fix. Codex's review of PR #248 found the feature could key the radio but a compound-call station's reply could never be decoded back into the QSO engine, plus three narrower correctness gaps. All fixed inline (round-1-unrestricted policy, `docs/DECISIONS/2026-08-07-pr-review-convergence-policy.md`):

- **Report/ack silently became a different message (P1)**: the round-1 `nrpt` fallback blanked ANY unrecognized `extra`, including a real numeric report/ack (`"-12"`, `"R-12"`) — silently sending a bare-pairing frame indistinguishable from a fresh CqResponse instead of the report the QSO needed to advance. `try_encode_nonstandard` now distinguishes `extra_is_grid_locator` (safe to drop) from `extra_is_numeric_report` (new helper, mirrors `packgrid`'s report parsing) — a report/ack now fails loudly (`Err`) instead of transmitting a different, misleading message. Round 2 deliberately did NOT add a watchdog-side "report-bearing state" heuristic for the residual case (a naive one, keyed on `metadata.their_callsign`, caused real false-positive test failures — see round 3 below, which found the correct scope for this check).
- **Decode-side routing (P1, the big one)**: three separate layers blocked a reply FROM a compound-call station from ever reaching the QSO engine, even though the encoder could now key a first frame TO one:
  - `Ft8Message::is_plausible` validated `NonStdCall` decodes with the SAME shape rule as `Standard` (`looks_like_callsign`: pack28's packed-encoding assumption, 3-6 chars with a single digit-position pattern) — rejecting real, correctly-decoded compound callsigns outright. New `looks_like_nonstandard_callsign` gives `NonStdCall` its own rule: `"CQ"`, a hash-render (`"<K5ARH>"`/`"<...>"`, bracket-wrapped), or the exact 58-bit form (≤11 chars, hash-callsign charset, digit AND letter present — kept in agreement with the encoder's `looks_like_callsign`).
  - `pancetta-qso/src/exchange.rs`'s regex patterns (`CQ_PATTERNS`/`QSO_PATTERNS`) and `validate_callsign` only accepted `[A-Z0-9/]+` — a hash-rendered callsign (`<`/`.`/`>`) never matched, so `parse_ft8_message` (the actual production decode→QSO-routing call, `pancetta/src/coordinator/qso.rs`) fell through to `NonStandard`/`Err` and the message never reached `process_message`. New shared `CALL_TOKEN` fragment (`[A-Z0-9/]+` OR a bracketed hash-render) and a `validate_callsign` bracket-shape branch.
  - The decoder's i3=4 hash table (`pancetta-ft8/src/message.rs::HashTable`, populated via `MessageParser::add_callsign`) was **never seeded in production** — `grep` across `decoder.rs` found zero call sites. Since our own (standard) callsign always lands in the lossy 12-bit hash slot when paired with a compound DX (the pack28-failing call always wins the exact slot), every reply addressed to us resolved to the unrecoverable `"<...>"` placeholder instead of our plain text — structurally unrecoverable, not a corner case. New `Ft8Decoder::seed_hash_callsign` (delegates to `self.message_parser.add_callsign` — every decode call path, including the parallel/rayon contexts, holds a `&MessageParser` *reference* into this same field, so seeding once reaches all of them) wired into `pancetta/src/coordinator/ft8.rs` at both decoder-construction sites (initial + the tier/protocol config-reload rebuild, which produces a fresh, unseeded decoder).
  - `pancetta_core::callsign::callsigns_match` (the `is_us`/`is_partner` sender-verification primitive) resolves a hash-render (`"<K5ARH>"` → `"K5ARH"`) before comparing, so a station's own callsign still matches once resolved; the unresolved placeholder `"<...>"` never matches anything (including another `"<...>"`) — it carries no identity information, and matching it would let unrelated traffic spoof as whichever station is being checked.
  - Proven end-to-end (not just an encoder-only round-trip), per the review's explicit ask: `pancetta/tests/loopback_qso.rs::test_loopback_compound_callsign_qso_advances_state_machine` drives a REAL encode → modulate → audio → decode → parse → `QsoManager::process_message` round trip both directions (DX CQs as `YS/WE9G`, we respond, DX decodes our reply — hash-resolving our callsign via the seeded table — and DX's own QSO state machine advances `CallingCq` → `WaitingForReport`).
- **Grid-bearing CQ from a compound operator (P1)**: if pancetta's OWN configured callsign is compound, `encode_cq`/`generate_message` render `"CQ <call> <grid>"` (3 tokens) — the round-1 CQ branch required exactly 2 tokens, so a compound-callsign OPERATOR could never call CQ at all. Now accepts an optional 3rd grid token and drops it (same pattern as the directed-message grid case).
- **Our own callsign unchecked in the watchdog (P2)**: `callsign_is_wire_representable` only validated `their_callsign`; `StationConfig` permits an arbitrarily long compound `our_callsign` with no length cap, so a misconfigured station callsign left every QSO — even against a perfectly normal DX — stuck on the slow generic timeout, the PAN-17 symptom moved to the other callsign. Now validates both sides.
- **Free-text corruption (P2)**: the round-1 `looks_like_callsign` heuristic (≥3 chars, a digit AND a letter, any position) was loose enough that `"HELLO1 WORLD2"` (valid 13-char free text) passed it and got silently transmitted as a WRONG type-4 callsign-hash frame instead of the requested free text. Tightened to require a real callsign shape — letters on BOTH sides of the digit block (a suffix letter after the last digit, mirroring `Ft8Message::looks_like_callsign`'s own suffix rule) — closing the gap while still accepting every PAN-17 incident callsign (`YS/WE9G`, `8G81PA`, `3E40CDW`).

Tests: `pancetta-ft8/src/encoder.rs` gained report-rejection, grid-bearing-CQ, and free-text-preservation regression tests; `pancetta-core/src/callsign.rs` gained hash-render match/reject tests; `pancetta-qso/src/exchange.rs` gained hash-render parse/validate tests; `pancetta/tests/loopback_qso.rs` gained the full round-trip test above.

### Round 3 (Codex re-review of the round-2 commit): 3 P1s, 2 P2s deferred to PAN-22

Codex re-reviewed round 2's remediation commit and found 3 NEW P1s — real progress that was still incomplete in specific ways — plus 2 P2s deferred to a follow-up ticket (PAN-22: a portable `/4`-suffix regression in `looks_like_callsign`, and interior-space plausibility in `message.rs`) per the round-2-defers-P2 convergence policy. All 3 P1s fixed inline:

1. **The PAN-17 symptom relocated to the report stage, still unguarded (P1)**: round 2's encoder fix (above) made a numeric report/ack to a compound-form partner fail loudly, but nothing stopped the QSO from re-arming that exact doomed encode every slot once it reached that rung — the original "burns the watchdog window retrying an unencodable message" failure, just moved past the initial-contact stage. Round 2 had deliberately skipped a report-stage watchdog check because a NAIVE version (keyed on `metadata.their_callsign`, the "most complete form ever seen") falsely retired healthy QSOs in `adversarial_compound_calls.rs`'s compound-then-base scenarios. The correct scope: new `report_stage_partner_callsign(state)` reads the STATE's OWN `their_callsign` field (`SendingReport`/`WaitingForReport`/`WaitingForConfirmation` only — the ONLY states whose associated message is a genuine numeric report/ack, never just RRR/RR73/73 or a droppable grid) — this is exactly the value `MessageExchange::generate_response` embeds in the real outgoing SignalReport/ReportAck, so the check fires if and only if the message the QSO is actually about to (re-)send is genuinely unencodable, never on a metadata-level guess. New `callsign_is_plausibly_pack28_standard` (length 3-6 after stripping a bare `/P`/`/R` suffix, no other `/`) decides "genuinely compound" in the safe direction (false positives only cost speed, falling back to the slower generic timeout; never wrongly retires a real standard callsign). This DID require updating `adversarial_compound_calls.rs`'s two positive scenarios (`compound_first_then_base_completes` → `..._reaches_report_stage_then_fails_fast`, `cqer_caller_compound_then_base_completes` → `..._reaches_report_stage_then_fails_fast`): both scenarios need a real numeric report addressed to a callsign that's compound at the moment the message is generated (`generate_response`'s report/ack arms all embed the STATE's latched `their_callsign`/`target_callsign` directly, never a freshened sender field) — round 1's encoder fix already made that impossible over real FT8; the sim harness just never exercised the real encoder before, so it didn't notice. The tests' actual regression guard (a compound↔base signing change doesn't spawn a duplicate QSO) is preserved and still asserted.
2. **Hash table only ever seeded with our own callsign (P1)**: when PANCETTA'S OWN configured callsign is compound and it calls CQ, a standard-callsign caller's type-4 reply puts the CALLER (not us) in the 12-bit hash field — but production only ever called `seed_hash_callsign` with our own callsign, never a caller we hadn't directly worked. `decode_window_with_ap_scoped_partner_impl` (the single choke point every public decode entry point funnels through — see round 2's note on why this matters) now also seeds the hash table from every `MessageType::Standard` decode's `to_callsign`/`from_callsign` this window (skipping CQ/DE/QRZ tokens), mirroring how WSJT-X/ft8_lib populate their hash tables from any successfully-decoded plain callsign, not just the operator's own. Proven with a decoder-level test (`decoder_seeds_hash_table_from_any_standard_decode_not_just_own_callsign`, decoder.rs) that decodes a standard-format CQ from a caller with NO explicit seeding, then confirms that caller's callsign resolves when it later lands in an i3=4 hash slot addressed to a compound operator.
3. **Resolved hash renders stayed bracketed in latched QSO state (P1)**: even once a caller's hash resolves (`"<K5ARH>"`), round 2's exchange-classification fix accepted the bracketed literal for *validation* purposes, but `determine_state_transition` then latched THAT literal — brackets included — as `their_callsign`. Outgoing message generation reuses that latched value, and round 2's own unencodable-message watchdog immediately classifies it as unrepresentable (`<`/`>` are outside the wire charset) — a resolved hash callsign was self-sabotaging via the very watchdog meant to protect it. New `normalize_callsign_token` (exchange.rs) unwraps a RESOLVED hash render to the plain callsign right at parse time, in both `parse_cq_message` and `parse_qso_message` (`captures.get(N)` → normalize → `MessageType`), before it can flow anywhere else — the unresolved placeholder `"<...>"` is left untouched (no real callsign to normalize it to). Proven end-to-end in `qso_manager.rs` (`resolved_hash_render_reply_latches_plain_callsign_not_bracketed`): parses a resolved-hash CqResponse, confirms the latched state carries the plain `"K1DEF"`, and — since that scenario also legitimately hits finding-1's report-stage watchdog (a compound OPERATOR can't receive a numeric report either, symmetric to the DX case) — confirms the retirement reason names the plain callsign and never mentions invalid characters, proving normalization ran before EITHER watchdog check saw it.

Tests: `pancetta-qso/src/qso_manager.rs` gained `callsign_is_plausibly_pack28_standard_boundary`, `report_stage_partner_callsign_extracts_from_report_bearing_states_only`, `report_stage_watchdog_retires_compound_partner`, `report_stage_watchdog_does_not_retire_standard_partner`, `report_stage_watchdog_does_not_retire_portable_suffix_partner`, and `resolved_hash_render_reply_latches_plain_callsign_not_bracketed`; `pancetta-qso/tests/adversarial_compound_calls.rs`'s two positive scenarios were updated to assert the corrected fast-fail behavior; `pancetta-qso/src/exchange.rs` gained `normalize_callsign_token_unwraps_resolved_hash_only` and an updated resolved-hash-reply test; `pancetta-ft8/src/decoder.rs` gained the any-caller hash-seeding test; `pancetta/tests/loopback_qso.rs`'s round-2 end-to-end test was updated to assert the now-normalized (unbracketed) latched partner callsign.

### Round 4 (Codex re-review): a never-before-heard caller's hash — investigated, not a bug

Codex's round-4 re-review asked pancetta to investigate, not assume: is "a standard-callsign station whose reply to a compound-callsign operator's CQ never resolves" (1) a pancetta ordering/scope bug in the round-3 seeding, or (2) an inherent i3=4 protocol limitation? **Determined to be (2)**, confirmed with real wire-level evidence, not just a claim:

- **The bit-level constraint**: a 12-bit hash is a one-way compression of a callsign into 4096 buckets. There is no way to reverse it without having independently learned the plaintext from a *different*, standard-format decode. When the OTHER party in an exchange is compound, the pack28-failing callsign always wins the exact 58-bit slot (`try_encode_nonstandard`'s doc) — so the standard-callsign side is *structurally* the one that lands in the hash slot, every time, for every message in that QSO. If a station's very first-ever transmission we've heard (this session, this band) is itself that i3=4 reply, there is no other bit anywhere in the 77-bit payload encoding their plaintext. WSJT-X has the identical limitation for the identical reason (its hash table also only ever grows from decoded plaintext) — this is not a pancetta gap to close, it's physics of the encoding.
- **Round 3's seeding is already exhaustive**: `Ft8Decoder::decode_window_with_ap_scoped_partner_impl`'s per-window loop seeds from *every* decoded `MessageType::Standard` callsign, from *any* frame heard, addressed to us or not — not just replies directed at us. There is no earlier opportunity (an ordering bug, a scope-too-narrow bug) for pancetta to exploit: if this station has *ever* transmitted a standard-format frame we've decoded (their own CQ, a QSO with a third party), they're already seeded before their reply to us arrives. The gap is real only when that has never happened — which is the (2) case, not fixable by more code.
- **Verified the QSO-layer behavior is a clean, bounded failure, not a hang**: traced `is_message_relevant`'s `(CallingCq, CqResponse)` arm — it deliberately does not validate the sender's identity (only that the response is addressed to us; we don't know who will answer a CQ yet) — so a reply carrying the literal unresolved placeholder `"<...>"` still advances the QSO and latches `their_callsign = "<...>"`. The PRE-EXISTING PAN-17 round-2 `callsign_is_wire_representable` watchdog check then retires it on the very next `check_timeouts_at` pass (`<`/`.`/`>` are outside the wire charset) — no new code needed; round 2's watchdog was already general enough to cover this case, just not previously proven against it.
- **Proven end-to-end, not just asserted**: `pancetta/tests/loopback_qso.rs::genuinely_unresolvable_caller_hash_never_resolves_but_retires_cleanly` drives a REAL encode → modulate → audio → decode round trip for a standard callsign (`K1DEF`) that the DX's decoder has never seen in any form, confirms the decoded text is genuinely `"YS/WE9G <...>"` (not asserted, observed), feeds it into the QSO engine, confirms the QSO latches the placeholder and advances to `WaitingForReport`, then confirms the watchdog retires it one pass later. The pre-existing `test_loopback_compound_callsign_qso_advances_state_machine` test's manual `seed_hash_callsign` call was *not* a crutch hiding this gap — it models the realistic case (the caller's plaintext already accumulated into the DX's hash table through ordinary band activity) — both tests now coexist, each proving a genuinely different, real scenario.

No code changes to the encoder/decoder/hash-table logic were needed or made — this section exists specifically so the limitation is documented (per the review's own request) and doesn't get "rediscovered" as a bug in a future review.
